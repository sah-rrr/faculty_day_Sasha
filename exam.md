## **📘 Лекции 1-2: БАЗА**

### **1) Какие базовые типы данных есть в Kotlin? Есть ли примитивы?**
**Ответ:**
В Kotlin все является объектом, но для производительности компилятор на этапе компиляции оптимизирует многие типы в примитивы JVM там, где это безопасно.

**Базовые типы делятся на категории:**

*   **Числовые:**
    *   Целые: `Byte`, `Short`, `Int`, `Long`
    *   С плавающей точкой: `Float`, `Double`
*   **Логический:** `Boolean`
*   **Символьный:** `Char`
*   **Строковый:** `String`
*   **Массивы:** `Array<T>`

**Про примитивы:** Да, Kotlin использует примитивные типы JVM (`int`, `double` и т.д.), но на уровне языка они представлены как классы. Это называется **"стирание боксинга" (inline classes)** или оптимизация. Когда вы пишете `val x: Int = 5`, в байт-коде это будет примитив `int`. Боксинг (преобразование в объект, например, `Int?` или при использовании в дженериках типа `List<Int>`) происходит только когда это необходимо.

**Пример:**
```kotlin
val a: Int = 100 // Примитив int в байт-коде
val b: Int? = 100 // Объект Integer в байт-коде (произошел боксинг)
val list: List<Int> = listOf(1, 2, 3) // Элементы будут запакованы в Integer
```

### **2) В чем разница между val и var? Когда нужно использовать val когда var?**
**Ответ:**
*   **`val` (value)** — **неизменяемая ссылка**. После инициализации значение не может быть изменено (как `final` в Java). **Содержимое объекта** при этом может меняться, если объект изменяемый.
*   **`var` (variable)** — **изменяемая ссылка**. Значение можно переприсваивать.

**Правила использования (Best Practices):**
1.  **Всегда начинайте с `val`.** Используйте `val` по умолчанию. Это делает код предсказуемым, безопасным для многопоточности и легче читаемым.
2.  **Используйте `var` только когда значение действительно должно меняться.** Например, счетчик в цикле, состояние UI-компонента, кэш.

**Пример:**
```kotlin
val immutableList = listOf(1, 2, 3) // Ссылка неизменна, список тоже
// immutableList.add(4) // Ошибка компиляции
// immutableList = anotherList // Ошибка компиляции

var mutableList = mutableListOf(1, 2, 3)
mutableList.add(4) // OK: меняется содержимое объекта
mutableList = mutableListOf(5, 6) // OK: меняется сама ссылка

val immutableReferenceToMutable = mutableListOf("a", "b")
immutableReferenceToMutable.add("c") // OK! Ссылка не меняется, но объект изменяемый.
```

### **3) Какие условные конструкции есть в языке?**
**Ответ:**
1.  **`if-else`** — классический условный оператор. **В Kotlin `if` является выражением** (expression), то есть возвращает значение.
    ```kotlin
    val max = if (a > b) {
        println("a больше")
        a // Возвращаемое значение
    } else {
        b
    }
    ```
2.  **`when`** — мощная замена `switch` из Java. Также является выражением.
    *   Проверка на равенство.
    *   Проверка на вхождение в диапазон (`in 1..10`).
    *   Проверка типа (`is String`).
    *   Можно использовать без аргумента как замену цепочке `if-else if`.
    ```kotlin
    val description = when (x) {
        1 -> "Один"
        in 2..10 -> "От двух до десяти"
        is String -> "Это строка длины ${x.length}"
        else -> "Что-то еще"
    }

    when {
        x.isOdd() -> print("x нечетное")
        x.isEven() -> print("x четное")
        else -> print("x — ноль")
    }
    ```
3.  **Условный оператор `?:` (Элвис)** — используется для предоставления значения по умолчанию при `null`.
    ```kotlin
    val length: Int = nullableString?.length ?: 0 // Если null, то 0
    ```

### **4) Как работают операторы == и === в Kotlin?**
**Ответ:**
*   **`==` (структурное равенство):** Проверяет **равенство значений**. Для типов, отличных от примитивов, вызывает метод `.equals()`. Безопасен для `null`: `null == null` вернет `true`.
*   **`===` (референциальное равенство):** Проверяет, ссылаются ли две переменные на **один и тот же объект в памяти** (как `==` в Java для объектов).

**Пример:**
```kotlin
val a: String = "Hello"
val b: String = "Hello"
val c: String? = a

println(a == b)  // true, значения одинаковые
println(a === b) // true! Компилятор использует String Pool, так что это один объект.
println(a === c) // true, c ссылается на тот же объект, что и a

val list1 = listOf(1, 2, 3)
val list2 = listOf(1, 2, 3)
println(list1 == list2) // true, содержимое одинаковое
println(list1 === list2) // false, это два разных объекта в памяти
```

### **5) Что такое top-level функции и свойства?**
**Ответ:**
Это функции и свойства, которые объявляются **вне любого класса, объекта или интерфейса**, прямо на уровне файла (`.kt`).

*   **Top-level функции:** Позволяют создавать утилитарные функции без необходимости создавать класс-помощник (как `static` методы в Java). Например, `println()` или `listOf()` — это top-level функции из стандартной библиотеки Kotlin.
*   **Top-level свойства:** Позволяют хранить константы или состояние на уровне всего приложения. Для неизменяемых свойств (`val`) компилятор создает `public static final` поле в Java. Для изменяемых (`var`) — поле с геттером/сеттером.

**Пример (файл `Utils.kt`):**
```kotlin
// Top-level свойство (константа)
const val PI_APPROX = 3.1415

// Top-level функция
fun formatGreeting(name: String): String {
    return "Привет, $name!"
}

// В другом файле можно использовать напрямую
fun main() {
    println(PI_APPROX)
    println(formatGreeting("Анна"))
}
```
**Под капотом:** Компилятор Kotlin создаст Java-класс с именем `UtilsKt`, в котором будут статические методы `formatGreeting` и поле `PI_APPROX`.

## **🔄 Лекции 1-2: GIT**

### **1) Что такое репозиторий?**
**Ответ:** Репозиторий (репа) — это **хранилище всех файлов проекта вместе с историей их изменений**, которую Git сохраняет в специальной скрытой папке `.git`. Он содержит все коммиты, ветки, теги.

### **2) Что такое коммит?**
**Ответ:** Коммит — это **"снимок" (snapshot) состояния файлов в репозитории на определенный момент времени**. Каждый коммит имеет:
*   Уникальный хэш (например, `a1b2c3d`).
*   Автора.
*   Дата создания.
*   Сообщение (commit message), описывающее изменения.
*   Ссылку на родительский коммит(ы).
    Коммиты образуют цепочку — историю проекта.

### **3) Что такое ветка?**
**Ответ:** Ветка (branch) — это **подвижный указатель на определенный коммит**. Позволяет вести параллельные линии разработки. Основная ветка по умолчанию часто называется `main` или `master`. Создание новой ветки — это создание нового указателя, который начинает двигаться независимо.

### **4) Что такое ребейз?**
**Ответ:** Ребейз (rebase) — это операция **перемещения всей цепочки коммитов одной ветки на вершину другой ветки**. История при этом становится линейной (как будто работа велась последовательно), что упрощает ее чтение.
**Алгоритм:** Git временно убирает ваши коммиты, применяет новые коммиты из целевой ветки, а затем поочередно применяет ваши коммиты заново поверх них.
**⚠️ Опасно для уже опубликованных (push) коммитов**, так как переписывает историю.

### **5) Что такое форк?**
**Ответ:** Форк (fork) — это **полная копия чужого репозитория на GitHub/GitLab в ваш собственный аккаунт**. Позволяет свободно экспериментировать с проектом, не затрагивая оригинал. Основной способ внести вклад в open-source проекты: вы делаете форк, клонируете его себе, создаете ветку, вносите изменения, делаете пул-реквест (PR) в оригинальный репозиторий.

### **6) Что такое удаленный репозиторий? Что такое локальный репозиторий?**
**Ответ:**
*   **Локальный репозиторий** — находится на вашем компьютере (папка `.git`). Вы работаете с ним непосредственно.
*   **Удаленный репозиторий (remote)** — расположен на сервере (например, GitHub, GitLab). Служит для совместной работы, резервного копирования и распространения кода. Стандартное имя — `origin`.

### **7) Как подтянуть изменения в свой форк из исходного репозитория?**
**Ответ:**
1.  Добавить оригинальный репозиторий как дополнительный remote (часто называют `upstream`):
    ```bash
    git remote add upstream https://github.com/original_owner/original_repo.git
    ```
2.  Получить изменения из `upstream`:
    ```bash
    git fetch upstream
    ```
3.  Переключиться на свою основную ветку (например, `main`):
    ```bash
    git checkout main
    ```
4.  Слить изменения из `upstream/main` в свою ветку:
    ```bash
    git merge upstream/main
    ```
    Или сделать rebase:
    ```bash
    git rebase upstream/main
    ```
5.  Отправить обновленную историю в свой форк на GitHub (`origin`):
    ```bash
    git push origin main
    ```

### **8) Когда возникает конфликт при ребейзе/мердже? Как их решать?**
**Ответ:**
*   **Когда возникает:** Конфликт возникает, когда Git не может автоматически определить, как объединить изменения из двух разных коммитов, которые **изменяли одни и те же строки в одном и том же файле**.
*   **Как решать (в IntelliJ IDEA):**
    1.  При попытке merge/rebase Git сообщит о конфликте и прервет операцию.
    2.  Файлы с конфликтами будут помечены. В IDEA откроется **инструмент разрешения конфликтов** с тремя панелями:
        *   **Слева:** Ваша версия файла (из текущей ветки).
        *   **Справа:** Версия файла из той ветки, с которой сливаетесь.
        *   **Посередине:** Результирующая версия с блоками конфликта (`<<<<<<<`, `=======`, `>>>>>>>`).
    3.  **Ваша задача:** Для каждого конфликтного блока выбрать нужную версию (левую, правую) или вручную отредактировать итоговый код в центральной панели, убрав маркеры конфликта.
    4.  После разрешения всех конфликтов во всех файлах нужно **проиндексировать (add) измененные файлы** и **завершить операцию**:
        ```bash
        git add <имя_файла>
        git rebase --continue  # или git merge --continue / git commit
        ```

## **🏛️ Лекция 3: ООП**

### **1) Принципы ООП с примерами ОБЯЗАТЕЛЬНО**
**Ответ:**
ООП основано на четырех основных принципах:

1.  **Инкапсуляция (Encapsulation):**
    *   **Суть:** Сокрытие внутреннего состояния (данных) объекта и деталей реализации. Доступ к данным осуществляется только через публичные методы (интерфейс).
    *   **Цель:** Защита данных от некорректного использования, упрощение взаимодействия с объектом, возможность менять реализацию без изменения кода, который этим объектом пользуется.
    *   **Пример в Kotlin:** Использование `private` свойств и предоставление публичных методов `getter`/`setter` или других методов для работы с ними.
    ```kotlin
    class BankAccount {
        private var balance: Double = 0.0 // Инкапсулированное свойство

        fun deposit(amount: Double) {
            require(amount > 0) { "Сумма должна быть положительной" }
            balance += amount
        }

        fun withdraw(amount: Double): Boolean {
            if (amount > 0 && balance >= amount) {
                balance -= amount
                return true
            }
            return false
        }

        fun getBalance(): Double = balance // Контролируемый доступ
    }

    // Использование
    val account = BankAccount()
    account.deposit(1000.0)
    // account.balance = 1000000.0 // Ошибка компиляции! Прямой доступ запрещен.
    ```

2.  **Наследование (Inheritance):**
    *   **Суть:** Механизм, позволяющий создавать новый класс (дочерний, производный) на основе существующего (родительского, базового). Дочерний класс перенимает (наследует) свойства и методы родительского и может добавлять или изменять их.
    *   **Цель:** Повторное использование кода (DRY - Don't Repeat Yourself), создание иерархий классов.
    *   **Пример в Kotlin:** Ключевые слова `open` (разрешает наследование) и `override` (переопределение).
    ```kotlin
    open class Vehicle(val brand: String) {
        open fun startEngine() = println("$brand: Двигатель запущен")
    }

    class Car(brand: String, val model: String) : Vehicle(brand) {
        override fun startEngine() {
            super.startEngine()
            println("$brand $model: Готов к поездке")
        }
    }

    val myCar = Car("Toyota", "Camry")
    myCar.startEngine() // Выведет: Toyota: Двигатель запущен \n Toyota Camry: Готов к поездке
    ```

3.  **Полиморфизм (Polymorphism):**
    *   **Суть:** Возможность объектов с одинаковой спецификацией (один интерфейс или базовый класс) иметь различную реализацию. "Один интерфейс — множество реализаций".
    *   **Виды:**
        *   **Полиморфизм времени компиляции (статический):** Перегрузка методов (Overloading).
        *   **Полиморфизм времени выполнения (динамический):** Переопределение методов (Overriding).
    *   **Пример в Kotlin:**
    ```kotlin
    open class Shape {
        open fun draw() = println("Рисую фигуру")
    }
    class Circle : Shape() { override fun draw() = println("Рисую круг") }
    class Square : Shape() { override fun draw() = println("Рисую квадрат") }

    fun renderShapes(shapes: List<Shape>) {
        for (shape in shapes) {
            shape.draw() // Вызовется своя реализация для каждого типа
        }
    }

    val shapes: List<Shape> = listOf(Circle(), Square(), Circle())
    renderShapes(shapes)
    // Вывод: Рисую круг \n Рисую квадрат \n Рисую круг
    ```

4.  **Абстракция (Abstraction):**
    *   **Суть:** Выделение существенных характеристик объекта и игнорирование несущественных деталей. Создание модели, которая определяет структуру и поведение, скрывая сложность.
    *   **Цель:** Упрощение работы со сложными системами.
    *   **Пример в Kotlin:** Абстрактные классы (`abstract class`) и интерфейсы (`interface`).
    ```kotlin
    // Абстракция "Транспортное средство"
    interface Transport {
        fun move() // Абстрактный метод, реализация скрыта
        fun getMaxSpeed(): Int
    }

    class Bicycle : Transport {
        override fun move() = println("Кручу педали")
        override fun getMaxSpeed() = 30
    }

    class Airplane : Transport {
        override fun move() = println("Лечу по небу")
        override fun getMaxSpeed() = 900
    }

    // Мы работаем с абстракцией Transport, не вдаваясь в детали
    fun travel(transport: Transport) {
        println("Начинаем движение со скоростью до ${transport.getMaxSpeed()} км/ч")
        transport.move()
    }
    ```

### **2) Какие есть языковые конструкции, чтобы реализовать каждый принцип?**
**Ответ:**
*   **Инкапсуляция:** Модификаторы доступа (`private`, `protected`, `internal`, `public`), свойства с кастомными геттерами/сеттерами, `inner` классы (для доступа к внешнему контексту).
*   **Наследование:** Ключевые слова `:` (для указания родителя), `open` (разрешает наследование и переопределение), `override` (помечает переопределенный член).
*   **Полиморфизм:**
    *   *Переопределение (Overriding):* `open`/`override`.
    *   *Перегрузка (Overloading):* Несколько функций с одним именем, но разными параметрами. Это стандартная возможность языка.
    *   *Интерфейсы и абстрактные классы:* Основные инструменты для реализации полиморфизма.
*   **Абстракция:** `abstract class` (может содержать состояние и реализацию), `interface` (контракт, без состояния до Kotlin 1.4, с default-реализацией методов). Оба могут содержать абстрактные члены.

### **3) Расскажите про primary и secondary конструкторы**
**Ответ:**
*   **Primary конструктор:** Объявляется в заголовке класса сразу после имени. Может содержать параметры, которые автоматически становятся свойствами класса (если объявлены с `val`/`var`). Инициализация логики должна находиться в блоке `init {}`.
    ```kotlin
    class Person(val name: String, var age: Int) { // Primary конструктор
        init {
            require(age >= 0) { "Возраст не может быть отрицательным" }
        }
    }
    val person = Person("Иван", 25) // Создание через primary
    ```
*   **Secondary конструкторы:** Объявляются внутри тела класса с помощью ключевого слова `constructor`. Используются, когда нужно несколько способов создания объекта. **Обязаны прямо или косвенно вызывать primary конструктор через `this(...)`**. Если primary конструктора нет, они вызывают конструктор суперкласса `super(...)`.
    ```kotlin
    class Person(val name: String, var age: Int) {
        constructor(name: String) : this(name, 0) { // Вызывает primary
            println("Вторичный конструктор для $name")
        }
        constructor() : this("Гость") // Вызывает secondary выше
    }
    val guest = Person() // -> Person("Гость") -> Person("Гость", 0)
    ```

### **4) Что такое data class и зачем он нужен?**
**Ответ:**
`data class` — специальный класс, предназначенный **только для хранения данных (DTO, модель)**. Компилятор автоматически генерирует для его свойств (`val`/`var` в primary конструкторе) стандартные и полезные методы:
1.  **`equals()` / `hashCode()`:** Сравнивают объекты по содержимому (по значениям всех свойств).
2.  **`toString()`:** Красивое строковое представление, например, `Person(name=Иван, age=25)`.
3.  **`copy()`:** Создает копию объекта с возможностью изменить часть свойств. **Крайне важен для работы с иммутабельными объектами.**
4.  **`componentN()`:** Функции для деструктуризации (`val (name, age) = person`).

**Пример:**
```kotlin
data class Person(val name: String, val age: Int)

fun main() {
    val ivan = Person("Иван", 25)
    val petr = Person("Петр", 25)
    println(ivan) // Person(name=Иван, age=25)
    println(ivan == petr) // false (разное имя)
    val ivanOlder = ivan.copy(age = 26) // Создаем новый объект!
    println(ivanOlder) // Person(name=Иван, age=26)

    val (name, age) = ivan // Деструктуризация
    println("$name, $age лет") // Иван, 25 лет
}
```
**Ограничения:** Не может быть `abstract`, `open`, `sealed`, `inner`. Должен иметь как минимум один параметр в primary конструкторе.

### **5) Что такое sealed class и где её используют?**
**Ответ:**
`sealed class` (запечатанный класс) — это **абстрактный класс, набор наследников которого известен и ограничен на этапе компиляции**. Все его наследники должны быть объявлены **в том же файле**, что и сам sealed class (начиная с Kotlin 1.5, можно в одном пакете).

**Главная цель:** Представление **замкнутого (ограниченного) множества типов**, что идеально для моделирования состояний или иерархий "или-или".

**Где используют:**
*   **Результаты операций:** Успех/Ошибка.
*   **Состояния UI:** Загрузка, Успех, Ошибка.
*   **АСТ (Абстрактное синтаксическое дерево).**
*   **Команды/События в приложении.**

**Сила в выражении `when`:** Компилятор проверяет, что все ветки sealed-класса обработаны, и `else` не требуется (если вы обрабатываете все случаи).
```kotlin
sealed class NetworkResult<out T>
data class Success<T>(val data: T) : NetworkResult<T>()
data class Error(val message: String) : NetworkResult<Nothing>()

fun handleResult(result: NetworkResult<String>) {
    when (result) {
        is Success -> println("Данные: ${result.data}")
        is Error -> println("Ошибка: ${result.message}")
        // else НЕ НУЖЕН, компилятор знает, что других вариантов нет
    }
}
```

### **6) Что такое enum class в Kotlin?**
**Ответ:**
`enum class` — это тип, представляющий **фиксированный набор именованных констант (перечисление)**. Каждая константа — это объект этого класса.

**Особенности Kotlin:**
*   Может иметь свойства и методы.
*   Может реализовывать интерфейсы.
*   Константы могут быть объявлены со своими параметрами.
*   Имеет встроенные свойства: `name` (имя константы), `ordinal` (порядковый номер).
*   Методы: `values()` (все константы), `valueOf(name: String)`.

**Пример:**
```kotlin
enum class Direction(val degrees: Int) {
    NORTH(0), EAST(90), SOUTH(180), WEST(270); // Точка с запятой обязательна

    fun opposite(): Direction = when (this) {
        NORTH -> SOUTH
        EAST -> WEST
        SOUTH -> NORTH
        WEST -> EAST
    }
}

fun main() {
    val dir = Direction.EAST
    println(dir.degrees) // 90
    println(dir.opposite()) // WEST
    println(Direction.values().joinToString { it.name }) // NORTH, EAST, SOUTH, WEST
}
```

### **7) Что такое object?**
**Ответ:**
Ключевое слово `object` в Kotlin используется для создания **синглтона (Singleton)** — класса, который имеет только один экземпляр на все приложение.
*   Объявление `object` одновременно объявляет класс и создает его единственный экземпляр.
*   Не имеет конструкторов.
*   Идеален для утилитарных классов, фасадов, контейнеров настроек, логгеров.

**Пример:**
```kotlin
object Logger {
    private var logLevel = "INFO"
    fun setLevel(level: String) { logLevel = level }
    fun log(message: String) = println("[$logLevel] $message")
}

// Использование (обращение напрямую к имени объекта)
Logger.log("Приложение запущено")
Logger.setLevel("DEBUG")
```

### **8) Что такое companion object?**
**Ответ:**
`companion object` — это **объект, объявленный внутри класса**. Его члены (свойства и функции) могут быть вызваны **напрямую по имени класса**, без создания экземпляра (аналогично `static` в Java).
*   У класса может быть только один `companion object`.
*   Может иметь имя (`companion object Factory { ... }`), но обычно используется безымянный.
*   Может реализовывать интерфейсы.
*   Доступ к приватным членам внешнего класса.

**Пример:**
```kotlin
class MyClass {
    private val secret = 42

    companion object {
        const val CONSTANT = "Константа" // Аналог public static final
        fun create(): MyClass = MyClass() // Фабричный метод
        fun accessPrivate(obj: MyClass) = println("Секрет: ${obj.secret}") // Доступ к приватному
    }
}

fun main() {
    println(MyClass.CONSTANT) // Доступ через имя класса
    val obj = MyClass.create()
    MyClass.accessPrivate(obj) // Секрет: 42
}
```

### **9) Расскажите про property getters/setters**
**Ответ:**
В Kotlin свойства (`val`/`var`) — это не просто поля. Они имеют **геттеры (get)** и, для `var`, **сеттеры (set)**, которые можно кастомизировать.
*   **По умолчанию** геттер просто возвращает значение поля, а сеттер — присваивает.
*   **Кастомные аксессоры** позволяют добавлять логику при чтении или записи.

**Пример:**
```kotlin
class Rectangle(width: Int, height: Int) {
    var width: Int = width
        set(value) {
            require(value > 0) { "Ширина должна быть положительной" }
            field = value // `field` — специальное идентификатор для backing-поля
        }

    val area: Int // Свойство без backing-поля, только геттер
        get() = this.width * this.height

    var otherProp: String = ""
        private set // Сеттер можно сделать приватным
}

val rect = Rectangle(10, 5)
println(rect.area) // 50 (вычисляется при каждом обращении)
rect.width = 20 // OK
// rect.width = -5 // Выбросит IllegalArgumentException
// rect.otherProp = "new" // Ошибка компиляции: сеттер private
```

### **10) Какие модификаторы доступа есть в Kotlin?**
**Ответ:**
1.  **`public` (по умолчанию):** Виден везде.
2.  **`internal`:** Виден внутри **одного модуля** (набора исходных файлов, скомпилированных вместе). Это уникальная для Kotlin фича для модульной разработки.
3.  **`protected`:** Виден внутри класса и его наследников. **Важно:** В Kotlin `protected` члены **не видны внутри пакета**, как в Java.
4.  **`private`:** Виден только внутри области, где объявлен (файла для top-level, класса для членов класса).

**Таблица видимости:**
| Модификатор | Top-level объявление | Член класса |
| :--- | :--- | :--- |
| `public` | Видно везде | Видно везде |
| `internal` | Видно в модуле | Видно в модуле |
| `protected` | Не применимо | Видно в классе и подклассах |
| `private` | Видно в файле | Видно в классе |

### **11) Что такое open, final? Когда что применяется? Какой по умолчанию у классов?**
**Ответ:**
*   **`final`:** Класс или член класса, помеченный как `final`, **не может быть унаследован или переопределен.** В Kotlin **по умолчанию все классы и методы являются `final`**. Это принцип "запрещено по умолчанию" для лучшей безопасности и дизайна.
*   **`open`:** Чтобы разрешить наследование класса или переопределение метода/свойства, его нужно явно пометить как `open`.

**Применение:**
*   **Делайте классы и методы `final` по умолчанию.** Открывайте их (`open`) только когда вы сознательно проектируете класс для наследования (например, создаете библиотеку или фреймворк).
*   Это предотвращает случайное нарушение инвариантов класса в подклассах и соответствует принципу "Композиция предпочтительнее наследования".

**Пример:**
```kotlin
open class Shape { // Класс открыт для наследования
    open fun draw() { println("Рисую фигуру") } // Метод открыт для переопределения
    fun finalMethod() { println("Я final") } // Нельзя переопределить
}
class Circle : Shape() {
    override fun draw() { println("Рисую круг") }
    // override fun finalMethod() {} // Ошибка компиляции
}
```

### **12) Как переопределяются методы (override)?**
**Ответ:**
1.  Родительский метод должен быть помечен как `open`.
2.  В дочернем классе метод помечается ключевым словом `override`.
3.  Тип возвращаемого значения дочернего метода может быть **подтипом (ковариантным)** возвращаемого значения родительского метода.
4.  Можно вызвать реализацию родителя через `super.methodName()`.

```kotlin
open class Animal {
    open fun makeSound() = println("Some generic sound")
    open val species: String = "Animal"
}

class Cat : Animal() {
    override fun makeSound() {
        super.makeSound() // Можно вызвать родительскую реализацию
        println("Meow!")
    }
    override val species: String = "Felis catus" // Можно переопределять и свойства
}
```

### **13) Что такое delegation (делегирование) в Kotlin?**
**Ответ:**
Делегирование — это шаблон проектирования, при котором **объект передает часть своих обязанностей другому объекту (делегату)**. Kotlin поддерживает **делегирование на уровне языка** с помощью ключевого слова `by`.

**Основные виды:**
1.  **Делегирование реализации интерфейса:** Класс реализует интерфейс, но всю реализацию перепоручает другому объекту.
    ```kotlin
    interface Printer {
        fun print(message: String)
    }

    class ConsolePrinter : Printer {
        override fun print(message: String) = println(message)
    }

    class Application(printer: Printer) : Printer by printer {
        // Класс Application реализует Printer, но вся работа делегируется
        // объекту `printer`. Мы можем не писать override fun print.
    }

    val app = Application(ConsolePrinter())
    app.print("Привет!") // Вызовется ConsolePrinter.print()
    ```
2.  **Делегирование свойств (`by lazy`, `observable`, `vetoable`):** Наиболее известный пример — **ленивая инициализация `by lazy`**.
    ```kotlin
    val expensiveValue: String by lazy {
        println("Вычисляю значение...")
        "Результат тяжелых вычислений"
    }
    println(expensiveValue) // Выведет: "Вычисляю значение..." и "Результат..."
    println(expensiveValue) // Выведет только: "Результат..." (значение закэшировано)
    ```

**Преимущества:** Уменьшает шаблонный код, обеспечивает повторное использование, способствует композиции.

## **🧩 Лекция 4: Интерфейсы, абстрактные классы и SOLID**

### **1) SOLID обязательно с примерами**
**Ответ:**
SOLID — это набор из пяти принципов объектно-ориентированного проектирования, направленных на создание понятного, гибкого и поддерживаемого кода.

**1. S — Single Responsibility Principle (Принцип единственной ответственности)**
*   **Суть:** Класс должен иметь только одну причину для изменения, то есть отвечать за одну, четко определенную задачу.
*   **Проблема:** "Божественный класс", который делает всё.
*   **Пример:**
    ```kotlin
    // НЕПРАВИЛЬНО
    class Order {
        fun calculateTotal() { /* ... */ }
        fun printInvoice() { /* ... */ }
        fun saveToDatabase() { /* ... */ }
        fun sendEmail() { /* ... */ }
        // Этот класс меняется, если меняется логика расчета, печати, БД или рассылки.
    }

    // ПРАВИЛЬНО
    class Order(val items: List<Item>) {
        fun calculateTotal(): Double = items.sumOf { it.price }
    }
    class InvoicePrinter {
        fun print(order: Order) { /* ... */ } // Отвечает только за печать
    }
    class OrderRepository {
        fun save(order: Order) { /* ... */ } // Отвечает только за сохранение
    }
    class EmailService {
        fun sendConfirmation(order: Order) { /* ... */ } // Отвечает только за отправку
    }
    ```

**2. O — Open/Closed Principle (Принцип открытости/закрытости)**
*   **Суть:** Программные сущности (классы, модули, функции) должны быть **открыты для расширения, но закрыты для модификации**. Вы можете добавлять новое поведение, не изменяя существующий код.
*   **Проблема:** Добавление новой функциональности заставляет переписывать старый код.
*   **Пример (с использованием интерфейсов):**
    ```kotlin
    // НЕПРАВИЛЬНО
    class AreaCalculator {
        fun calculateArea(shape: Any): Double {
            return when (shape) {
                is Circle -> Math.PI * shape.radius * shape.radius
                is Square -> shape.side * shape.side
                else -> throw IllegalArgumentException()
                // Что будет, если добавить Triangle? Придется менять этот класс!
            }
        }
    }

    // ПРАВИЛЬНО
    interface Shape {
        fun area(): Double // Закрыто для модификации (интерфейс фиксирован)
    }
    class Circle(val radius: Double) : Shape {
        override fun area() = Math.PI * radius * radius
    }
    class Square(val side: Double) : Shape {
        override fun area() = side * side
    }
    class Triangle(val base: Double, val height: Double) : Shape {
        override fun area() = 0.5 * base * height // Расширение: новый класс
    }

    class AreaCalculator {
        fun calculateTotalArea(shapes: List<Shape>): Double {
            return shapes.sumOf { it.area() } // Код калькулятора не меняется!
        }
    }
    ```

**3. L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
*   **Суть:** Объекты базового класса должны быть заменяемы объектами производных классов без изменения корректности программы. **Наследник не должен ужесточать предусловия или ослаблять постусловия.**
*   **Проблема:** Квадрат-прямоугольник, пингвин-птица, которые не умеют летать.
*   **Пример:**
    ```kotlin
    // НЕПРАВИЛЬНО
    open class Bird {
        open fun fly() { println("Лечу") }
    }
    class Penguin : Bird() {
        override fun fly() {
            throw UnsupportedOperationException("Пингвины не летают!") // Нарушает LSP!
        }
    }
    fun makeBirdFly(bird: Bird) { bird.fly() } // Упадет для Penguin

    // ПРАВИЛЬНО (пересматриваем иерархию)
    open class Bird
    interface FlyingBird {
        fun fly() // Выделяем летающих птиц в отдельный интерфейс
    }
    class Eagle : Bird(), FlyingBird {
        override fun fly() = println("Орел парит")
    }
    class Penguin : Bird() // Пингвин — просто птица, он не обязан летать.
    fun makeBirdFly(bird: FlyingBird) { bird.fly() } // Принимает только тех, кто точно умеет
    ```

**4. I — Interface Segregation Principle (Принцип разделения интерфейсов)**
*   **Суть:** Клиенты не должны зависеть от методов, которые они не используют. Вместо одного "толстого" интерфейса лучше создать несколько маленьких и специфичных.
*   **Проблема:** Интерфейс `Worker` с методами `work()`, `eat()`, `sleep()`. Роботу не нужны `eat()` и `sleep()`.
*   **Пример:**
    ```kotlin
    // НЕПРАВИЛЬНО
    interface Worker {
        fun work()
        fun eat()
    }
    class Human : Worker {
        override fun work() { println("Человек работает") }
        override fun eat() { println("Человек ест") }
    }
    class Robot : Worker {
        override fun work() { println("Робот работает") }
        override fun eat() { /* Робот не ест! Пустой метод или исключение */ }
    }

    // ПРАВИЛЬНО
    interface Workable { fun work() }
    interface Eatable { fun eat() }

    class Human : Workable, Eatable {
        override fun work() { println("Человек работает") }
        override fun eat() { println("Человек ест") }
    }
    class Robot : Workable {
        override fun work() { println("Робот работает") } // Реализует только нужное
    }
    ```

**5. D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
*   **Суть:**
    1.  Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.
    2.  Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.
*   **Проблема:** Класс напрямую создает экземпляры конкретных классов.
*   **Пример:**
    ```kotlin
    // НЕПРАВИЛЬНО (зависимость от деталей)
    class PaymentService {
        private val processor = PayPalProcessor() // Жесткая привязка
        fun process(amount: Double) = processor.processPayment(amount)
    }

    // ПРАВИЛЬНО (зависимость от абстракции)
    interface PaymentProcessor {
        fun processPayment(amount: Double): Boolean
    }
    class PayPalProcessor : PaymentProcessor { /* ... */ }
    class StripeProcessor : PaymentProcessor { /* ... */ }

    // Модуль верхнего уровня зависит от интерфейса (абстракции)
    class PaymentService(private val processor: PaymentProcessor) { // Внедрение зависимости
        fun process(amount: Double) = processor.processPayment(amount)
    }

    // Теперь можно легко подменить реализацию
    val service1 = PaymentService(PayPalProcessor())
    val service2 = PaymentService(StripeProcessor())
    // Код тестируем (можно передать Mock)
    ```

### **2) Интерфейсы и их особенности с примерами**
**Ответ:**
**Интерфейс в Kotlin** — это контракт, который класс обязуется выполнить. Он определяет **что** можно делать, но не **как** (за исключением методов с реализацией по умолчанию).

**Особенности и синтаксис:**
1.  **Абстрактные методы:** Без тела.
2.  **Методы с реализацией по умолчанию (default-методы):** Начиная с Kotlin 1.0 (в Java с 8).
3.  **Свойства:** Могут быть абстрактными (`val prop: Int`) или иметь аксессоры по умолчанию.
4.  **Наследование интерфейсов:** Интерфейс может наследовать другие интерфейсы.
5.  **Функциональные (SAM) интерфейсы:** Интерфейс с одним абстрактным методом. Для них работает синтаксис лямбд.

**Пример:**
```kotlin
interface Vehicle {
    val brand: String // Абстрактное свойство
    val maxSpeed: Int
        get() = 200 // Свойство с геттером по умолчанию

    fun start() // Абстрактный метод
    fun stop() {
        println("$brand остановился") // Метод с реализацией по умолчанию
    }
}

interface Electric {
    fun charge()
}

// Наследование интерфейсов и реализация
class TeslaCar : Vehicle, Electric {
    override val brand = "Tesla"
    // maxSpeed использует реализацию по умолчанию

    override fun start() = println("Tesla запущен бесшумно")
    override fun charge() = println("Заряжаюсь на станции")
    // stop() использует реализацию по умолчанию
}

// SAM-интерфейс
fun interface StringPredicate {
    fun test(str: String): Boolean
}
val isEmpty = StringPredicate { it.isEmpty() } // Создание через лямбду
```

### **3) Абстрактные классы и их особенности с примерами**
**Ответ:**
**Абстрактный класс** — это класс, который нельзя инстанциировать напрямую. Он служит базой для других классов и может содержать как абстрактные члены (без реализации), так и конкретные (с реализацией).

**Отличия от интерфейсов (ключевые особенности):**
1.  **Может иметь состояние:** Свойства с backing field.
2.  **Конструктор:** Может иметь primary и secondary конструкторы.
3.  **Наследование:** Класс может наследовать только один абстрактный класс.
4.  **Модификаторы доступа:** Члены могут быть `private`, `protected` и т.д.

**Когда использовать?** Когда у классов-наследников есть **общее состояние или поведение**, которое вы хотите инкапсулировать в базовом классе.

**Пример:**
```kotlin
abstract class AbstractFileOpener {
    // Конкретное свойство с состоянием
    protected var lastOpenedFile: String? = null

    // Абстрактный метод (должен быть реализован наследниками)
    abstract fun open(filePath: String): Boolean

    // Конкретный метод с общей логикой
    fun logOpening(filePath: String) {
        println("Попытка открыть файл: $filePath")
        lastOpenedFile = filePath
    }

    // Может иметь конструктор
    init {
        println("Абстрактный файловый менеджер инициализирован")
    }
}

class PdfOpener : AbstractFileOpener() {
    override fun open(filePath: String): Boolean {
        logOpening(filePath) // Используем общую логику
        println("Открываю PDF: $filePath")
        return filePath.endsWith(".pdf")
    }
}

val opener = PdfOpener()
opener.open("document.pdf")
// Вывод:
// Абстрактный файловый менеджер инициализирован
// Попытка открыть файл: document.pdf
// Открываю PDF: document.pdf
```

### **4) Интерфейсы vs Абстрактные классы с примерами**
**Ответ:**
Выбор зависит от задачи. Вот сравнительная таблица:

| Критерий | Интерфейс | Абстрактный класс |
| :--- | :--- | :--- |
| **Состояние** | Не может хранить состояние (поля) до Kotlin 1.4, с 1.4 может через свойства с аксессорами, но **без backing field**. | **Может** иметь поля (состояние). |
| **Конструктор** | Нет конструктора. | **Может** иметь конструктор. |
| **Наследование** | Класс может реализовывать **много** интерфейсов. | Класс может наследовать только **один** абстрактный класс. |
| **По умолчанию** | Все члены `public abstract` (если без тела). | Могут быть любые модификаторы. |
| **Когда использовать** | Для определения **контракта** (способности). Для полиморфизма. Когда нет общего состояния. | Когда есть **общая логика и состояние** для группы родственных классов. Для шаблонного метода (Template Method). |

**Пример дилеммы и решения:**
```kotlin
// Ситуация: Есть разные документы с общими атрибутами и разными способами печати.

// ПЛОХО: Используем только интерфейс. Придется дублировать общие поля в каждом классе.

    val author: String

}

abstract class Document(
    open val title: String,
    open val author: String
) // Общее состояние

class TextDocument(
    override val title: String,
    override val author: String,

class Spreadsheet(
    override val title: String,
    override val author: String,

) : Document(title, author), Printable {

// Теперь легко добавить другой тип документа, и он получит title/author от Document,
// а также может не реализовывать Printable, если он не для печати.
```

**Вывод:** Используйте **интерфейсы** для определения возможностей (`CanFly`, `CanSwim`), а **абстрактные классы** для выделения общей структуры и кода в иерархии объектов (`Vehicle`, `BaseFragment`, `Repository`). Часто их используют вместе.

## **🚨 Лекция 5: Обработка исключений**

### **1) Какие есть исключения?**
**Ответ:**
В Kotlin (как и в Java) все исключения являются наследниками класса `Throwable`. Иерархия выглядит так:

```
Throwable
├── Error (Ошибки)
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── ...
└── Exception (Исключения)
    ├── IOException (Checked)
    │   ├── FileNotFoundException
    │   └── EOFException
    ├── SQLException (Checked)
    └── RuntimeException (Unchecked)
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IllegalStateException
        ├── IndexOutOfBoundsException
        └── ...
```

**Ключевые отличия:**
*   **`Error` (Ошибки):** Критические системные проблемы, которые обычно не могут (и не должны) обрабатываться в коде приложения (например, нехватка памяти). Представляют собой **непроверяемые (unchecked)** исключения.
*   **`Exception` (Исключения):** Проблемы в логике программы, которые можно и нужно обрабатывать.
    *   **Checked Exceptions (Проверяемые):** Наследники `Exception`, кроме `RuntimeException`. **Kotlin НЕ ИМЕЕТ checked исключений!** В Kotlin все исключения — **unchecked**. Компилятор не заставляет вас объявлять или ловить их. Это одно из ключевых отличий от Java.
    *   **Unchecked Exceptions (Непроверяемые):** `RuntimeException` и его наследники. Возникают из-за ошибок программиста (обращение к `null`, неверный аргумент, выход за границы массива).

### **2) Как их можно обрабатывать?**
**Ответ:**
Основные конструкции для обработки исключений в Kotlin:

1.  **`try-catch-finally`:**
    ```kotlin
    fun readFile(path: String): String? {
        var reader: BufferedReader? = null
        return try {
            reader = File(path).bufferedReader()
            reader.readLine() // Может выбросить IOException
        } catch (e: FileNotFoundException) {
            println("Файл не найден: ${e.message}")
            null
        } catch (e: IOException) {
            println("Ошибка ввода-вывода: ${e.message}")
            null
        } catch (e: Exception) { // Более общий обработчик
            println("Неизвестная ошибка: ${e.message}")
            null
        } finally {
            println("Операция чтения завершена.")
            reader?.close() // Важно освобождать ресурсы в finally
        }
    }
    ```
    *   **`try`:** Блок, в котором может возникнуть исключение.
    *   **`catch`:** Блок, обрабатывающий исключение определенного типа. Может быть несколько блоков `catch`. Исключения обрабатываются сверху вниз, от более конкретных к более общим.
    *   **`finally`:** Блок, который выполняется **всегда**, независимо от того, было ли выброшено исключение. Используется для освобождения ресурсов (закрытие файлов, соединений и т.д.).

2.  **`throw`:**
    ```kotlin
    fun divide(a: Int, b: Int): Int {
        if (b == 0) {
            throw IllegalArgumentException("Делить на ноль нельзя!")
        }
        return a / b
    }
    ```

3.  **`try` как выражение (expression):** В Kotlin `try-catch` может возвращать значение.
    ```kotlin
    val number = try {
        "123".toInt() // Если успешно, вернет 123
    } catch (e: NumberFormatException) {
        -1 // Если ошибка, вернет -1
    }
    println(number) // 123

    val invalid = try {
        "abc".toInt()
    } catch (e: NumberFormatException) {
        -1
    }
    println(invalid) // -1
    ```

### **3) Расскажите про runCatching и Result<T>**
**Ответ:**
`runCatching` — это функция стандартной библиотеки Kotlin, которая предоставляет **функциональный (декларативный)** способ обработки исключений. Она возвращает специальный тип `Result<T>`.

**`Result<T>`** — это sealed class, который может быть в одном из двух состояний:
*   `Success(value: T)` — содержит успешный результат.
*   `Failure(exception: Throwable)` — содержит исключение.

**Преимущества:**
*   Позволяет обрабатывать ошибки **без использования блоков `try-catch`**.
*   Позволяет строить **цепочки обработки** (как с `Optional` в Java).
*   Более функциональный и декларативный стиль.

**Методы `Result<T>`:**
*   `isSuccess` / `isFailure` — проверка состояния.
*   `getOrNull()` — возвращает результат или `null` при ошибке.
*   `exceptionOrNull()` — возвращает исключение или `null` при успехе.
*   `getOrDefault(defaultValue)` — возвращает результат или значение по умолчанию.
*   `getOrElse { block }` — возвращает результат или вычисляет его из блока.
*   `getOrThrow()` — возвращает результат или бросает исключение.
*   `map { }` / `mapCatching { }` — преобразует успешное значение. `mapCatching` ловит исключения внутри себя.
*   `recover { }` / `recoverCatching { }` — обрабатывает ошибку, возвращая успешный `Result`.
*   `fold(onSuccess = { }, onFailure = { })` — обрабатывает оба случая.

**Пример:**
```kotlin
fun parseNumber(str: String): Result<Int> = runCatching {
    str.toInt()
}

fun main() {
    val result = parseNumber("123")
        .map { it * 2 } // Если успех, умножаем на 2
        .recover { exception -> // Если была ошибка, восстанавливаемся
            println("Ошибка парсинга: ${exception.message}. Использую 0.")
            0
        }
        .getOrThrow() // Получаем итоговое значение

    println(result) // 246

    // Более компактный пример
    val value = runCatching { "abc".toInt() }
        .getOrDefault(-1)
    println(value) // -1

    // Обработка через fold
    runCatching { riskyOperation() }.fold(
        onSuccess = { println("Успех: $it") },
        onFailure = { println("Провал: ${it.message}") }
    )
}
```

### **4) Что такое Unit и Nothing**
**Ответ:**
*   **`Unit`:** Тип, который соответствует **отсутствию значимого значения**. Аналог `void` в Java, но является **полноценным типом** (синглтон `Unit`). Используется, когда функция ничего не возвращает.
    ```kotlin
    fun log(message: String): Unit { // : Unit можно не писать, это подразумевается
        println(message)
        // Неявно возвращается объект Unit
    }
    val u: Unit = log("Hello") // Это корректно
    ```
    Важность `Unit` как типа проявляется в обобщенном программировании. Например, `List<Unit>` — это допустимый тип, список, содержащий только объекты `Unit`.

*   **`Nothing`:** Тип, который **не имеет ни одного значения**. Он представляет собой **результат, который никогда не будет получен**. Используется для обозначения:
    1.  **Функций, которые никогда не завершаются нормально** (всегда бросают исключение или зацикливаются).
    2.  **Выражений, которые всегда завершаются с ошибкой** (например, `throw`).
    3.  В обобщенном программировании для обозначения **пустых коллекций** (например, `List<Nothing>` — это пустой список, безопасный для чтения, но в него нельзя ничего добавить).
    ```kotlin
    fun fail(message: String): Nothing {
        throw IllegalStateException(message) // Функция всегда бросает исключение
    }

    fun example(x: String?): String {
        val nonNull = x ?: fail("x is null") // Тип выражения ?: — String
        // Компилятор знает, что если x был null, выполнение не дойдет сюда.
        // Поэтому nonNull имеет тип String (не String?)
        return nonNull.uppercase()
    }

    val emptyList: List<Nothing> = listOf() // Пустой список
    // val item = emptyList[0] // Не скомпилируется, потому что значения типа Nothing не существует.
    ```

**`Nothing?`** — это тип, который может содержать только одно значение: `null`. Это самый "нижний" тип в иерархии типов Kotlin, подтип всех nullable-типов.

### **5) Зачем нужны исключения**
**Ответ:**
Исключения нужны для **обработки ошибок и нестандартных ситуаций** в программе, отделяя нормальный поток выполнения от кода обработки ошибок.

**Основные цели:**
1.  **Отделение ошибок от основного кода:** Без исключений каждая функция должна была бы возвращать специальный код ошибки, а вызывающий код постоянно проверять его. Это загромождает логику.
2.  **Передача ошибки вверх по стеку вызовов:** Ошибка может быть обработана не там, где возникла, а на более высоком уровне, где есть достаточно контекста для принятия решения (например, показать сообщение пользователю).
3.  **Группировка и классификация ошибок:** Иерархия исключений позволяет ловить ошибки как группами (`IOException`), так и по отдельности (`FileNotFoundException`).
4.  **Гарантия безопасности ресурсов:** Блок `finally` позволяет гарантированно освобождать ресурсы (файлы, соединения, блокировки) даже в случае возникновения ошибки.
5.  **Информирование о нарушениях контракта:** Исключения типа `IllegalArgumentException` или `IllegalStateException` четко сигнализируют о том, что были нарушены условия работы метода или объекта.

**Пример преимущества перед кодами ошибок:**
```kotlin
// Без исключений (плохо)
fun transferMoney(accountFrom: Account, accountTo: Account, amount: Int): Int {
    if (amount <= 0) return -1 // Код ошибки: неверная сумма
    if (accountFrom.balance < amount) return -2 // Код ошибки: недостаточно средств
    // ... логика перевода
    return 0 // Успех
}

// С исключениями (лучше)
fun transferMoney(accountFrom: Account, accountTo: Account, amount: Int) {
    require(amount > 0) { "Сумма перевода должна быть положительной" }
    check(accountFrom.balance >= amount) { "Недостаточно средств на счете" }
    // ... логика перевода
    // В случае ошибки выполнение прервется, вызывающий код поймает исключение
}
```

## **📦 Лекция 6: Коллекции**

### **1) Иерархия коллекций Kotlin**
**Ответ:**
В Kotlin есть две иерархии коллекций: **изменяемая (mutable)** и **неизменяемая (immutable)**. Kotlin разделяет интерфейсы только для чтения и для записи.

**Базовые интерфейсы:**
*   `Iterable<T>` — может предоставить итератор (для циклов).
*   `Collection<T>` — расширяет `Iterable`, добавляет размер, проверку на пустоту, наличие элемента.
*   `List<T>` — упорядоченная коллекция с доступом по индексу.
*   `Set<T>` — коллекция уникальных элементов.
*   `Map<K, V>` — коллекция пар ключ-значение, ключи уникальны.

Для изменяемых коллекций существуют соответствующие интерфейсы с префиксом `Mutable-`:
*   `MutableIterable<T>`
*   `MutableCollection<T>`
*   `MutableList<T>`
*   `MutableSet<T>`
*   `MutableMap<K, V>`

**Схема иерархии (упрощенно):**
```
          Iterable<T>           →    MutableIterable<T>
               ↓                           ↓
          Collection<T>        →    MutableCollection<T>
          /         \                     /         \
     List<T>       Set<T>       MutableList<T>   MutableSet<T>
                                     ↓                ↓
                                ArrayList<T>    HashSet<T>
                                     ...             ...

     Map<K, V>              →    MutableMap<K, V>
         ↓                           ↓
    HashMap<K, V>               HashMap<K, V>
```

**Важно:** В Kotlin `List` по умолчанию — **интерфейс только для чтения**. Функции типа `listOf()` возвращают **неизменяемый список**. Для создания изменяемого списка нужно использовать `mutableListOf()` или `arrayListOf()`.

### **2) Иерархия коллекций Java**
**Ответ:**
В Java одна основная иерархия, где интерфейсы обычно содержат как методы чтения, так и записи.

**Основные интерфейсы:**
*   `Iterable<T>` → `Collection<T>`
*   `Collection<T>` → `List<T>`, `Set<T>`, `Queue<T>`
*   `Map<K, V>` (не наследует `Collection`)

**Популярные реализации:**
*   **List:** `ArrayList`, `LinkedList`, `Vector` (устарел)
*   **Set:** `HashSet`, `LinkedHashSet`, `TreeSet`
*   **Map:** `HashMap`, `LinkedHashMap`, `TreeMap`, `Hashtable` (устарел)
*   **Queue:** `LinkedList`, `PriorityQueue`, `ArrayDeque`

**Связь с Kotlin:** Коллекции Kotlin на JVM — это **те же самые Java-коллекции**, но Kotlin добавляет к ним свои extension-функции (`map`, `filter` и т.д.) и разделяет интерфейсы на read-only и mutable на уровне Kotlin-типов.

### **3) Знать как устроены все коллекции (из иерархии Java) на примере хэш сета (что такое бакеты, когда используется хэш функция а когда equals, коллизии)**
**Ответ:**
Возьмем для примера **`HashSet`** (и его аналог `HashMap`).

**Как устроен HashSet/HashMap:**
1.  **Внутреннее хранилище:** Массив (часто называют "table") фиксированного размера из "корзин" (buckets). Каждая корзина — это обычно связный список (в Java 8+ может быть сбалансированное дерево при большом количестве коллизий).
2.  **Добавление элемента (в `HashSet`):**
    *   Вычисляется **хэш-код** элемента (метод `hashCode()`).
    *   На основе хэш-кода вычисляется **индекс корзины** в массиве: `index = hashCode() % tableSize`.
    *   Элемент помещается в соответствующую корзину. Если в корзине уже есть элементы — происходит **коллизия**.
3.  **Поиск элемента:**
    *   Вычисляется хэш-код искомого элемента.
    *   Находится корзина по индексу.
    *   В корзине происходит **последовательный перебор элементов** и сравнение с помощью **`equals()`**.

**Роль `hashCode()` и `equals()`:**
*   **`hashCode()` используется только для определения номера корзины (bucket).** Он должен быть быстрым и давать равномерное распределение.
*   **`equals()` используется для точного сравнения элементов внутри корзины.** Он должен быть точным.
*   **Критически важный контракт:** Если `a.equals(b) == true`, то обязательно `a.hashCode() == b.hashCode()`. Обратное не обязательно: равные хэш-коды не гарантируют равенство объектов.

**Коллизии:** Это ситуация, когда разные объекты имеют одинаковый хэш-код (или разные хэш-коды, но попали в одну корзину). В этом случае элементы складываются в одну корзину (связный список). При большом количестве коллизий производительность деградирует до O(n). Хорошая хэш-функция и правильно sized таблица минимизируют коллизии.

**Пример с `HashMap<String, Value>`:**
```kotlin
val map = HashMap<String, Int>()
map.put("apple", 1)
// 1. hashCode() для "apple" -> допустим, 12345
// 2. index = 12345 % 16 = 9 (если размер таблицы 16)
// 3. В bucket[9] помещается Entry("apple", 1)

map.get("apple")
// 1. hashCode("apple") -> 12345
// 2. index = 9
// 3. В bucket[9] ищется элемент, где key.equals("apple") == true
```

### **4) Знать какие реализации Java используются в Kotlin**
**Ответ:**
Kotlin не создает свои реализации, а использует стандартные Java-коллекции. Конкретные реализации:
*   **`listOf()`** → возвращает экземпляр **`java.util.Arrays$ArrayList`** (неизменяемый обертка вокруг массива) или `kotlin.collections.EmptyList` для пустого списка.
*   **`mutableListOf()`, `arrayListOf()`** → **`java.util.ArrayList`**.
*   **`setOf()`** → **`java.util.LinkedHashSet`** (сохраняет порядок вставки) или `kotlin.collections.EmptySet`.
*   **`mutableSetOf()`, `hashSetOf()`** → **`java.util.HashSet`**.
*   **`linkedSetOf()`** → **`java.util.LinkedHashSet`**.
*   **`sortedSetOf()`** → **`java.util.TreeSet`**.
*   **`mapOf()`** → **`java.util.LinkedHashMap`** (сохраняет порядок) или `kotlin.collections.EmptyMap`.
*   **`mutableMapOf()`, `hashMapOf()`** → **`java.util.HashMap`**.
*   **`linkedMapOf()`** → **`java.util.LinkedHashMap`**.
*   **`sortedMapOf()`** → **`java.util.TreeMap`**.

**Важно:** Функции типа `listOf` возвращают **неизменяемые** с точки зрения Kotlin коллекции, но на уровне JVM это те же `ArrayList`. Kotlin просто не предоставляет через свой интерфейс `List` методов изменения, хотя при касте к `java.util.List` или использовании Java-кода их можно изменить.

### **5) O - нотация. Знать сложность операций вставки в начало/середину/конец, получение элемента из начала/середины/конца и другие операции**
**Ответ:**
**O-нотация (Big O)** описывает **асимптотическую сложность алгоритма** — как растет время выполнения (или потребление памяти) при увеличении размера входных данных (n).

**Основные сложности операций для стандартных коллекций:**

| Структура / Операция                | Доступ по индексу | Поиск по значению/ключу | Вставка в начало | Вставка в конец | Удаление элемента |
| :---------------------------------- | :---------------- | :---------------------- | :--------------- | :-------------- | :---------------- |
| **`ArrayList` (изменяемый список)** | **O(1)**          | O(n)                    | O(n)             | **O(1)** (амортизированно) | O(n)              |
| **`LinkedList`**                    | O(n)              | O(n)                    | **O(1)**         | **O(1)**        | O(1) (если есть ссылка) |
| **`HashSet` / `HashMap`**           | Не применимо      | **O(1)** (в среднем)    | Не применимо     | **O(1)** (в среднем) | **O(1)** (в среднем) |
| **`TreeSet` / `TreeMap`**           | Не применимо      | **O(log n)**            | Не применимо     | **O(log n)**    | **O(log n)**      |

**Пояснения и нюансы:**
*   **`ArrayList`:**
    *   Доступ по индексу O(1), так как это массив.
    *   Вставка в начало/середину O(n), потому что нужно сдвигать все последующие элементы.
    *   Вставка в конец O(1) **амортизированно**. При заполнении массива происходит его увеличение (копирование) за O(n), но если рассматривать много операций добавления, средняя стоимость — O(1).
*   **`LinkedList`:**
    *   Доступ по индексу O(n), так как нужно пройти от начала списка.
    *   Вставка/удаление в известной позиции (если у вас есть ссылка на узел) — O(1).
*   **`HashSet/HashMap`:**
    *   Операции O(1) **в среднем при хорошей хэш-функции и отсутствии коллизий**. В худшем случае (все элементы в одной корзине) — O(n).
*   **`TreeSet/TreeMap`:**
    *   Основаны на красно-черном дереве. Операции гарантированно O(log n), что предсказуемо, но медленнее, чем у хэш-таблиц.

**Пример для понимания:**
```kotlin
val arrayList = arrayListOf(1, 2, 3, 4, 5)
arrayList[2] // O(1) - мгновенный доступ к 3-му элементу
arrayList.contains(5) // O(n) - нужно проверить все элементы
arrayList.add(0, 10) // O(n) - сдвиг всех 5 элементов

val linkedList = LinkedList(listOf(1, 2, 3, 4, 5))
linkedList[2] // O(n) - нужно пройти 2 узла от начала
linkedList.addFirst(10) // O(1) - просто меняем ссылку head

val hashSet = hashSetOf(1, 2, 3, 4, 5)
hashSet.contains(5) // O(1) - вычисляем хэш, идем в корзину
```

**Важно для экзамена:** Уметь обосновать выбор коллекции. Например:
*   Нужен частый доступ по индексу? → `ArrayList`.
*   Частые вставки/удаления в начале? → `LinkedList`.
*   Нужно быстро проверять наличие элемента? → `HashSet`.
*   Нужны элементы отсортированными? → `TreeSet`.

## **🎯 Лекция 7: Функциональное программирование**

### **1) Лямбда функции и как это реализовано под капотом**
**Ответ:**
**Лямбда-функция (лямбда)** — это анонимная функция (без имени), которую можно передавать как значение. Синтаксис: `{ параметры -> тело }`.

**Как это реализовано под капотом:**
1.  **Для Java-интерфейсов (SAM):** Если лямбда передается в Java-метод, ожидающий интерфейс с одним методом (например, `Runnable`), компилятор Kotlin создает анонимный класс, реализующий этот интерфейс.
2.  **Для Kotlin-функций:** Компилятор использует **инлайнинг (inline)**. Если функция, принимающая лямбду, помечена как `inline`, тело лямбды вставляется напрямую в место вызова, **без создания дополнительных объектов**. Это ключевая оптимизация в Kotlin.
3.  **Без инлайнинга:** Если функция не `inline`, для каждой лямбды создается объект анонимного класса (экземпляр `FunctionN`, где N — количество параметров). Это может повлиять на производительность.

**Пример и дизассемблирование:**
```kotlin
// Kotlin код
fun main() {
    val list = listOf(1, 2, 3)
    val result = list.map { it * 2 } // Лямбда
    println(result)
}
```
Под капотом для `map` (которая inline) не создается объектов для лямбды. Код будет развернут примерно так:
```kotlin
val result = ArrayList<Int>()
for (item in list) {
    result.add(item * 2) // Тело лямбды вставлено прямо здесь
}
```

**Вывод:** Kotlin старается оптимизировать лямбды через инлайнинг, что делает их эффективными. Но если функция не `inline` (например, некоторые функции из Java-библиотек), будет создан объект.

### **2) Знать основные функции (map, filter и тд - подробнее см. лекции)**
**Ответ:**
Все эти функции — extension-функции для коллекций и последовательностей. Они **не модифицируют исходную коллекцию**, а возвращают новую.

#### **Основные категории:**

**1. Трансформации (Transformations):**
*   **`map { }`** — преобразует каждый элемент.
    ```kotlin
    listOf(1, 2, 3).map { it * 2 } // [2, 4, 6]
    ```
*   **`mapNotNull { }`** — преобразует и отфильтровывает `null`.
    ```kotlin
    listOf("1", "two", "3").mapNotNull { it.toIntOrNull() } // [1, 3]
    ```
*   **`flatMap { }`** — преобразует каждый элемент в коллекцию и "склеивает" результаты.
    ```kotlin
    listOf("Hello", "World").flatMap { it.toList() } // [H, e, l, l, o, W, o, r, l, d]
    ```
*   **`flatten()`** — склеивает коллекцию коллекций.
    ```kotlin
    listOf(listOf(1, 2), listOf(3, 4)).flatten() // [1, 2, 3, 4]
    ```
*   **`zip()`** — объединяет две коллекции в пары.
    ```kotlin
    listOf("A", "B").zip(listOf(1, 2)) // [(A, 1), (B, 2)]
    ```

**2. Фильтрация (Filtering):**
*   **`filter { }`** — оставляет элементы, удовлетворяющие условию.
    ```kotlin
    listOf(1, 2, 3, 4).filter { it % 2 == 0 } // [2, 4]
    ```
*   **`filterNot { }`** — противоположность `filter`.
*   **`filterIsInstance<T>()`** — фильтрует по типу.
    ```kotlin
    listOf(1, "two", 3).filterIsInstance<String>() // ["two"]
    ```
*   **`take(n)`** — берет первые n элементов.
*   **`drop(n)`** — пропускает первые n элементов.
*   **`takeWhile { }` / `dropWhile { }`** — берут/пропускают, пока условие истинно.

**3. Поиск и проверки (Searching & Checking):**
*   **`find { }` / `firstOrNull { }`** — первый элемент, удовлетворяющий условию, или `null`.
*   **`lastOrNull { }`** — последний элемент по условию.
*   **`any { }`** — true, если хотя бы один элемент удовлетворяет условию.
*   **`all { }`** — true, если все элементы удовлетворяют условию.
*   **`none { }`** — true, если ни один элемент не удовлетворяет условию.
*   **`contains(element)`** — проверка наличия элемента.

**4. Группировка и агрегация (Grouping & Aggregation):**
*   **`groupBy { }`** — группирует элементы в `Map` по ключу.
    ```kotlin
    listOf("apple", "banana", "apricot").groupBy { it.first() }
    // {a=[apple, apricot], b=[banana]}
    ```
*   **`associateBy { }`** — создает Map, где ключ — результат лямбды, а значение — сам элемент. **Ключи должны быть уникальными!**
*   **`partition { }`** — разделяет на две коллекции по условию.
    ```kotlin
    val (even, odd) = listOf(1, 2, 3, 4).partition { it % 2 == 0 }
    // even = [2, 4], odd = [1, 3]
    ```
*   **`reduce { acc, value -> }`** — последовательно применяет операцию ко всем элементам, начиная с первого.
    ```kotlin
    listOf(1, 2, 3, 4).reduce { acc, i -> acc + i } // 10 (сумма)
    ```
*   **`fold(initial) { acc, value -> }`** — то же, что `reduce`, но с начальным значением.
    ```kotlin
    listOf(1, 2, 3).fold(10) { acc, i -> acc + i } // 16 (10 + 1 + 2 + 3)
    ```
*   **`sum(), average(), min(), max(), count()`** — специальные агрегаты.

**5. Сортировка (Sorting):**
*   **`sorted()`** — сортировка по естественному порядку (для `Comparable`).
*   **`sortedBy { }`** — сортировка по ключу.
*   **`sortedDescending()`, `sortedByDescending { }`** — обратная сортировка.

### **3) Знать Sequence и чем они отличаются от коллекций. Когда их стоит применять?**
**Ответ:**
**Sequence (последовательность)** — это ленивый аналог коллекций. Элементы вычисляются по мере необходимости (on-demand).

**Ключевые отличия от коллекций:**

| Характеристика | Коллекция (например, List) | Sequence |
| :--- | :--- | :--- |
| **Вычисления** | **Eager (жадные)** — операции выполняются сразу и возвращают новую коллекцию. | **Lazy (ленивые)** — операции откладываются до запроса результата (терминальной операции). |
| **Промежуточные результаты** | Создаются новые коллекции на каждом шаге. | Не создаются промежуточные коллекции, операции "цепляются" в конвейер. |
| **Порядок обработки** | Весь список проходит через одну операцию, затем через следующую (vertically). | Каждый элемент проходит через всю цепочку операций по очереди (horizontally). |
| **Многократный проход** | Можно итерировать много раз. | Обычно только один проход (после завершения итерации её нужно начать заново). |
| **Null-безопасность** | Операции типа `mapNotNull`. | Те же операции, но ленивые. |

**Пример, показывающий разницу:**
```kotlin
val list = listOf(1, 2, 3, 4, 5)

// КОЛЛЕКЦИЯ: Eager evaluation
val result1 = list
    .map { println("map $it"); it * 2 } // ВСЕ элементы умножаются сразу
    .filter { println("filter $it"); it > 5 } // ВСЕ элементы фильтруются
// Вывод: map 1, map 2, map 3, map 4, map 5, filter 2, filter 4, filter 6, filter 8, filter 10

// SEQUENCE: Lazy evaluation
val result2 = list.asSequence()
    .map { println("map $it"); it * 2 }
    .filter { println("filter $it"); it > 5 }
    .toList() // Терминальная операция — только здесь начинаются вычисления
// Вывод для КАЖДОГО элемента по цепочке: map 1, filter 2, map 2, filter 4, map 3, filter 6
// Дальше элементы не обрабатываются, т.к. найдено нужное количество
```

**Когда использовать Sequence:**
1.  **Большие коллекции** (тысячи+ элементов) — экономия памяти за счет отсутствия промежуточных коллекций.
2.  **Длинные цепочки операций** — особенно с `filter` в начале, что может сократить количество обрабатываемых элементов.
3.  **Инфинитные последовательности** — генерируемые последовательности (например, `generateSequence`).

**Когда НЕ использовать:**
1.  **Маленькие коллекции** — накладные расходы на создание Sequence могут перевесить выгоду.
2.  **Когда нужен доступ по индексу** — у Sequence нет индексов.
3.  **Когда нужно многократно итерировать** — каждый раз придется запускать конвейер заново.

### **4) let, also, with, apply, run**
**Ответ:**
Это **scope-функции** — функции, которые выполняют блок кода в контексте некоторого объекта. Они отличаются **способом передачи объекта в блок** (как `this` или `it`) и **возвращаемым значением**.

**Сравнительная таблица:**

| Функция | Контекст (получатель) | Возвращаемое значение | Типичное использование |
| :--- | :--- | :--- | :--- |
| **`let`** | `it` (можно переименовать) | Результат лямбды | Преобразование, работа с nullable, ограничение скоупа |
| **`also`** | `it` | Сам объект (`this`) | Дополнительные действия, побочные эффекты, логирование |
| **`with`** | `this` | Результат лямбды | Группировка операций над объектом без необходимости в результате |
| **`apply`** | `this` | Сам объект (`this`) | Инициализация объекта, настройка свойств |
| **`run`** | `this` | Результат лямбды | Комбинация `with` и `let`: и вычисление, и работа с `this` |

**Примеры:**
```kotlin
// let — преобразование, безопасная работа с nullable
val length = nullableString?.let { 
    println("Длина строки: ${it.length}") 
    it.length 
} ?: 0

// also — побочные эффекты
val list = mutableListOf<Int>().also {
    it.add(1)
    it.add(2)
    println("Список создан: $it")
}

// with — группировка операций
val builder = StringBuilder()
with(builder) {
    append("Hello")
    append(" ")
    append("World")
    toString() // Возвращается последнее выражение
}

// apply — инициализация объекта
val person = Person().apply {
    name = "Alice"
    age = 30
    // возвращается this (объект Person)
}

// run — вычисление результата с контекстом
val result = person.run {
    println("Имя: $name")
    name.length // возвращается длина имени
}
```

**Как выбрать:**
*   Нужно **инициализировать или настроить** объект? → `apply`
*   Нужно **вычислить что-то с объектом** и вернуть результат? → `run` или `with`
*   Нужно **преобразовать объект**? → `let`
*   Нужно сделать **побочный эффект** (логирование, валидация)? → `also`
*   Работаете с **nullable**? → `let` с безопасным вызовом `?.let`

### **5) Что происходит под капотом, когда к коллекции применяется функция .map или любая другая**
**Ответ:**
Рассмотрим на примере **не-inline** функции (хотя большинство функций коллекций — inline).

1.  **Создается промежуточная коллекция:** Например, для `list.map { ... }` создается новый `ArrayList`.
2.  **Итерация:** Происходит итерация по исходной коллекции.
3.  **Применение лямбды:** Для каждого элемента вызывается переданная лямбда-функция.
4.  **Добавление результата:** Результат лямбды добавляется в новую коллекцию.
5.  **Возврат:** Возвращается новая коллекция.

**Важно:** Для **inline-функций** (как `map` в стандартной библиотеке Kotlin) компилятор **не создает промежуточные объекты для лямбд**, а **встраивает код лямбды прямо в цикл**. Однако сама новая коллекция для результатов все равно создается.

**Пример (упрощенное представление работы `map`):**
```kotlin
// Примерная реализация map (не настоящая)
inline fun <T, R> Iterable<T>.map(transform: (T) -> R): List<R> {
    val destination = ArrayList<R>()
    for (item in this) {
        destination.add(transform(item)) // transform встроится сюда
    }
    return destination
}
```

**Что происходит при цепочке вызовов:**
```kotlin
list.map { it * 2 }.filter { it > 5 }
```
1.  Создается коллекция №1 после `map`.
2.  Создается коллекция №2 после `filter`.
3.  Возвращается коллекция №2.

Именно поэтому для больших коллекций и длинных цепочек выгодно использовать `Sequence` — не создаются промежуточные коллекции.

### **6) Что такое destructuring declaration в коллекциях?**
**Ответ:**
**Destructuring declaration (деструктурирующее объявление)** — это синтаксис, позволяющий **разложить объект на несколько переменных**. Для коллекций это работает, потому что у `List` и `Map.Entry` есть специальные функции `component1()`, `component2()` и т.д.

**Примеры:**
```kotlin
// Деструктуризация списка (только для первых N элементов)
val list = listOf("Alice", "Bob", "Charlie")
val (first, second) = list
println("$first, $second") // Alice, Bob

// Деструктуризация map entry
val map = mapOf("name" to "Alice", "age" to 30)
for ((key, value) in map) {
    println("$key -> $value")
}
// name -> Alice
// age -> 30

// Пропуск элементов с помощью _
val (_, third) = list
println(third) // Charlie
```

**Под капотом:** Компилятор преобразует деструктуризацию в вызовы `componentN()`:
```kotlin
val (first, second) = list
// преобразуется в:
val first = list.component1()
val second = list.component2()
```

**Ограничения:** Деструктуризация работает только для **data-классов**, **коллекций** и любых других классов, у которых объявлены операторы `componentN()`.

### **7) infix**
**Ответ:**
**`infix`** — модификатор, позволяющий вызывать функцию с **одним параметром** в инфиксной нотации (без точки и скобок). Это делает код более читаемым, похожим на естественный язык.

**Условия:**
1.  Функция-член класса или extension-функция.
2.  Имеет ровно **один параметр**.
3.  Не может быть `vararg` параметром.

**Примеры:**
```kotlin
// Объявление infix-функции
infix fun Int.times(str: String) = str.repeat(this)

// Использование
println(2 times "Bye ") // Bye Bye
// Эквивалентно: 2.times("Bye ")

// Стандартные примеры: to, until, step
val map = mapOf("key" to "value") // to — это infix-функция
val range = 1 until 10
```

**Когда использовать:** Для DSL (предметно-ориентированных языков), операций, которые читаются как естественный язык (например, `user hasRole "admin"`).

### **8) inline**
**Ответ:**
**`inline`** — модификатор, который указывает компилятору **встраивать тело функции в место её вызова**, вместо генерации обычного вызова функции. Используется в основном для функций высшего порядка (принимающих лямбды).

**Зачем нужно:**
1.  **Устранение накладных расходов на лямбды:** Без `inline` для каждой лямбды создается объект анонимного класса. С `inline` код лямбды встраивается напрямую.
2.  **Возможность использовать `reified` типы:** Только inline-функции могут иметь параметры типа с модификатором `reified`, которые сохраняют информацию о типе во время выполнения.
3.  **Контроль потока выполнения:** В inline-функции можно использовать `return`, который возвращается из внешней функции (non-local return).

**Пример:**
```kotlin
inline fun <T> measureTime(block: () -> T): T {
    val start = System.currentTimeMillis()
    val result = block() // Тело блока встроится сюда
    val end = System.currentTimeMillis()
    println("Время выполнения: ${end - start} мс")
    return result
}

// Вызов
val result = measureTime {
    // Этот код будет встроен прямо в место вызова
    heavyComputation()
}
```

**Предостережения:** Не стоит помечать как `inline` большие функции, так как это увеличит размер итогового байткода. Также inline-функции не могут использовать некоторые возможности (например, вызывать себя рекурсивно).

### **9) tailrec**
**Ответ:**
**`tailrec`** — модификатор, указывающий компилятору на **хвостовую рекурсию** (tail recursion). Компилятор оптимизирует хвостовую рекурсию в **итеративный цикл**, что предотвращает переполнение стека при глубокой рекурсии.

**Условия хвостовой рекурсии:**
1.  Последняя операция в функции — вызов самой себя (рекурсивный вызов).
2.  Не должно быть дополнительных операций после рекурсивного вызова.
3.  Нельзя использовать `try/catch/finally` с рекурсивным вызовом внутри.

**Пример:**
```kotlin
// Без tailrec (опасность StackOverflowError для больших n)
fun factorial(n: Int): Long = if (n <= 1) 1 else n * factorial(n - 1)

// С tailrec (оптимизируется в цикл)
tailrec fun factorialTailRec(n: Int, accumulator: Long = 1): Long {
    return if (n <= 1) accumulator 
    else factorialTailRec(n - 1, n * accumulator) // Последняя операция — рекурсивный вызов
}

// Вызов
println(factorialTailRec(10000)) // Работает без переполнения стека
```

**Как работает оптимизация:** Компилятор преобразует рекурсию в цикл:
```kotlin
// Примерная оптимизация
fun factorialIterative(n: Int): Long {
    var acc = 1L
    var current = n
    while (current > 1) {
        acc *= current
        current--
    }
    return acc
}
```

**Когда использовать:** Для рекурсивных алгоритмов, где глубина рекурсии может быть большой (обход деревьев, математические вычисления).

## **🛡️ Лекция 8: Null-safety, расширения, Gradle, тестирование**

### **1) Что такое null safety? Зачем нужно?**
**Ответ:**
**Null safety** — это система типов в Kotlin, разработанная для **исключения `NullPointerException` (NPE)** во время выполнения. В Kotlin типы по умолчанию **не nullable** — переменная не может содержать `null`, если это явно не разрешено.

**Зачем нужно:**
1.  **Предотвращение NPE:** `NullPointerException` — одна из самых частых ошибок в Java. Kotlin решает эту проблему на уровне системы типов.
2.  **Четкость кода:** Явно видно, какие переменные могут быть `null`, а какие нет.
3.  **Безопасность:** Компилятор заставляет обрабатывать возможные `null` значения.
4.  **Упрощение рефакторинга:** При изменении кода компилятор сразу покажет, где может возникнуть проблема с `null`.

**Пример:**
```kotlin
// В Kotlin String ≠ String?
var nonNullable: String = "Hello"
// nonNullable = null // Ошибка компиляции

var nullable: String? = "Hello"
nullable = null // OK
```

### **2) Расскажите про реализацию null safety в Kotlin (типы с ?, :?, !!, .?)**
**Ответ:**
Котлин предоставляет несколько операторов для безопасной работы с nullable-типами:

**1. Безопасный вызов (Safe call) — `?.`**
Выполняет операцию только если объект не `null`.
```kotlin
val length: Int? = nullableString?.length
// Если nullableString == null, то length = null
// Если nullableString != null, то length = nullableString.length
```

**2. Элвис-оператор (Elvis operator) — `?:`**
Предоставляет значение по умолчанию при `null`.
```kotlin
val length: Int = nullableString?.length ?: 0
// Если nullableString?.length вернет null, то length = 0
```

**3. Утверждение "не-null" (Not-null assertion) — `!!`**
Говорит компилятору: "Я уверен, что это не null". Если объект все же `null`, выбрасывает `NullPointerException`.
```kotlin
val length: Int = nullableString!!.length // Опасный оператор!
// Использовать только когда точно уверены, иначе риск NPE
```

**4. Безопасный каст (Safe cast) — `as?`**
Пытается привести к типу, при неудаче возвращает `null`.
```kotlin
val obj: Any = "Hello"
val str: String? = obj as? String // String
val num: Int? = obj as? Int // null
```

**5. Проверка на null в условии (Smart cast)**
После проверки на `null` компилятор автоматически делает smart cast.
```kotlin
fun printLength(str: String?) {
    if (str != null) {
        println(str.length) // Smart cast: str теперь String, а не String?
    }
}
```

### **3) Функции-расширения. Примеры**
**Ответ:**
**Extension-функции** — функции, которые можно добавлять к существующим классам без наследования или изменения исходного кода класса. Синтаксис: `fun Тип.имяФункции() { ... }`

**Примеры:**
```kotlin
// Добавляем функцию to строке
fun String.addExclamation(): String = "$this!"

println("Hello".addExclamation()) // Hello!

// Добавляем функцию к List
fun <T> List<T>.penultimate(): T {
    if (size < 2) throw NoSuchElementException()
    return this[size - 2]
}

val list = listOf(1, 2, 3, 4)
println(list.penultimate()) // 3

// Extension-свойства
val String.isPalindrome: Boolean
    get() = this == reversed()

println("radar".isPalindrome) // true
```

**Особенности:**
1.  **Статическая диспетчеризация:** Вызываются как статические функции, привязанные к типу, а не к объекту.
2.  **Не имеют доступа к приватным членам:** Могут работать только с публичным API класса.
3.  **Могут быть объявлены где угодно:** В файлах, внутри классов, объектов.
4.  **Приоритет:** Если в классе уже есть функция с таким же именем, будет вызвана она, а не extension.

**Под капотом:** Extension-функция компилируется в обычную статическую функцию с первым параметром — receiver.
```kotlin
// Котлин:
fun String.addExclamation(): String = "$this!"

// Java-эквивалент:
public static String addExclamation(String receiver) {
    return receiver + "!";
}
```

### **4) Smart cast**
**Ответ:**
**Smart cast (умное приведение)** — автоматическое приведение типа компилятором после проверки. Работает для:
1.  **Проверки на `null`** (самый частый случай).
2.  **Проверки типа с `is`**.
3.  **Вызовов `!is`** (не является типом).
4.  **Ветвлений `when`**.

**Примеры:**
```kotlin
// 1. Проверка на null
fun processString(str: String?) {
    if (str != null) {
        // Компилятор автоматически делает str: String
        println(str.length) // OK
    }
    
    // Или
    str?.let { 
        // Внутри блока it: String (не String?)
        println(it.length)
    }
}

// 2. Проверка типа
fun process(obj: Any) {
    if (obj is String) {
        // Компилятор делает smart cast к String
        println(obj.length) // OK, obj теперь String
    }
    
    if (obj !is String) return
    // Здесь obj тоже автоматически String
    println(obj.uppercase())
}

// 3. В when выражении
when (obj) {
    is String -> println(obj.length) // Smart cast к String
    is Int -> println(obj.inc())     // Smart cast к Int
    else -> println("Unknown type")
}
```

**Ограничения smart cast:**
1.  Не работает с **`var` свойствами класса**, если они могут быть изменены из другого потока.
2.  Не работает с **свойствами, имеющими кастомные геттеры**, которые могут возвращать разные значения.
```kotlin
var global: String? = "Hello"

fun tricky() {
    if (global != null) {
        // Ошибка компиляции! global мог измениться в другом потоке
        // println(global.length)
        
        // Нужно использовать безопасный вызов или локальную переменную
        println(global?.length)
        
        val local = global
        if (local != null) {
            println(local.length) // OK, локальная переменная
        }
    }
}
```

### **5) Что такое late initialization (lateinit)?**
**Ответ:**
**`lateinit`** — модификатор, позволяющий отложить инициализацию `non-null` переменной до момента после создания объекта. Используется, когда переменную нельзя инициализировать в конструкторе, но вы гарантируете, что она будет инициализирована до первого использования.

**Когда использовать:**
1.  **Внедрение зависимостей** (например, поля, которые инициализируются через Dagger/Spring).
2.  **Инициализация в методах жизненного цикла** (например, `onCreate()` в Android).
3.  **Setup в unit-тестах** (`@BeforeEach`).

**Пример:**
```kotlin
class MyService {
    lateinit var dependency: Dependency
    
    fun initialize(dep: Dependency) {
        dependency = dep
    }
    
    fun action() {
        // Гарантируем, что initialize() был вызван до action()
        dependency.doWork()
    }
}

// В Android
class MainActivity : AppCompatActivity() {
    private lateinit var adapter: RecyclerViewAdapter
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        adapter = RecyclerViewAdapter() // Инициализация
        recyclerView.adapter = adapter
    }
}
```

**Ограничения и особенности:**
1.  **Только для `var`** (не для `val`).
2.  **Только для non-nullable типов** (нельзя `lateinit var str: String?`).
3.  **Нельзя использовать с примитивами** (Int, Boolean и т.д.).
4.  **Проверка инициализированности:** `::variable.isInitialized`.
```kotlin
lateinit var data: String

fun process() {
    if (::data.isInitialized) {
        println(data.length)
    } else {
        println("Data not initialized")
    }
}
```

**Если обратиться к `lateinit` переменной до инициализации:** Будет выброшено `UninitializedPropertyAccessException`.

**Альтернатива для примитивов:** Для отложенной инициализации примитивов используйте `by lazy` или nullable тип с значением по умолчанию.

### **Gradle**

### **1) Что это и зачем нужно? Основная сущность Gradle?**
**Ответ:**
**Gradle** — это система автоматической сборки (build automation tool). Она используется для:
1.  **Компиляции** исходного кода.
2.  **Управления зависимостями** (библиотеками).
3.  **Запуска тестов**.
4.  **Создания дистрибутивов** (JAR, APK, WAR и т.д.).
5.  **Деплоя** приложений.

**Основная сущность Gradle — задача (Task).** Задача представляет собой некоторое действие (компиляция, копирование файлов, запуск тестов). Задачи могут зависеть друг от друга, образуя граф зависимостей.

**Конфигурация Gradle** пишется на **Kotlin DSL** (ранее использовался Groovy) в файлах:
- `settings.gradle.kts` — настройки проекта (модули).
- `build.gradle.kts` — конфигурация сборки для каждого модуля.

### **2) Какие задачи вы знаете? (build, clean, test и тд)**
**Ответ:**
Основные задачи Gradle:

| Задача | Описание |
| :--- | :--- |
| **`clean`** | Удаляет папку `build` (очищает результаты предыдущих сборок). |
| **`build`** | Полная сборка проекта: компиляция, запуск тестов, создание артефактов. |
| **`assemble`** | Собирает артефакты (JAR, WAR и т.д.) без запуска тестов. |
| **`compileJava` / `compileKotlin`** | Компилирует Java/Kotlin код. |
| **`test`** | Запускает unit-тесты. |
| **`check`** | Запускает все проверки (тесты, статический анализ). |
| **`run`** | Запускает приложение (если это application, а не library). |
| **`dependencies`** | Показывает дерево зависимостей проекта. |

**Пример использования в терминале:**
```bash
./gradlew clean build      # Очистить и собрать полностью
./gradlew test             # Только запустить тесты
./gradlew run              # Запустить приложение
```

### **3) Что такое плагин? Что такое зависимость? В чем разница?**
**Ответ:**

**Плагин (Plugin)** — это **расширение функциональности Gradle**. Плагины добавляют новые задачи, конфигурации, возможности сборки.
- **Примеры:** `java`, `kotlin`, `application`, `spring-boot`, `compose`.
- **Назначение:** Определяет **как** собирается проект.

**Зависимость (Dependency)** — это **внешняя библиотека, которую использует ваш проект**.
- **Примеры:** `org.jetbrains.kotlin:kotlin-stdlib`, `junit:junit:4.13.2`.
- **Назначение:** Определяет **что** используется в проекте.

**Разница:**
- **Плагин** изменяет процесс сборки (добавляет задачи).
- **Зависимость** добавляет код, который будет использован в вашем приложении.

**Пример в `build.gradle.kts`:**
```kotlin
plugins {
    kotlin("jvm") version "1.9.0" // ПЛАГИН: добавляет поддержку Kotlin
    application                    // ПЛАГИН: добавляет задачу 'run'
}

dependencies {
    implementation("org.jetbrains.kotlin:kotlin-stdlib") // ЗАВИСИМОСТЬ: библиотека Kotlin
    testImplementation("junit:junit:4.13.2")             // ЗАВИСИМОСТЬ: библиотека для тестов
}
```

### **4) Как организовать многомодульный проект? (можно на примере нашей репы)**
**Ответ:**
**Многомодульный проект** — проект, состоящий из нескольких взаимосвязанных модулей (subprojects).

**Структура:**
```
my-project/
├── settings.gradle.kts          # Регистрирует модули
├── build.gradle.kts             # Общая конфигурация для всех модулей (необязательно)
├── core/                        # Модуль 1
│   ├── build.gradle.kts
│   └── src/
├── api/                         # Модуль 2
│   ├── build.gradle.kts
│   └── src/
└── app/                         # Главный модуль
    ├── build.gradle.kts
    └── src/
```

**`settings.gradle.kts`:**
```kotlin
rootProject.name = "my-project"

include(":core")  // Модуль core
include(":api")   // Модуль api  
include(":app")   // Модуль app
```

**Зависимости между модулями в `build.gradle.kts`:**
```kotlin
// В модуле app
dependencies {
    implementation(project(":core"))  // Зависимость от модуля core
    implementation(project(":api"))   // Зависимость от модуля api
}

// В модуле api
dependencies {
    implementation(project(":core"))  // api зависит от core
}
```

**Преимущества многомодульности:**
1.  **Разделение ответственности:** Каждый модуль решает свою задачу.
2.  **Повторное использование:** Модули можно использовать в других проектах.
3.  **Ускорение сборки:** Gradle кэширует модули, которые не изменились.
4.  **Изоляция:** Можно иметь разные версии зависимостей в разных модулях.

### **5) Откуда Gradle берет зависимости?**
**Ответ:**
Gradle ищет зависимости в **репозиториях (repositories)**. По умолчанию обычно настроены:

1.  **Maven Central (`mavenCentral()`)** — основной публичный репозиторий для Java/Kotlin библиотек.
2.  **Google Maven (`google()`)** — для Android-библиотек и других библиотек от Google.
3.  **JCenter (`jcenter()`)** — устарел, но еще может использоваться (переход на Maven Central).
4.  **Локальный репозиторий (`mavenLocal()`)** — зависимости, установленные локально (через `mvn install`).
5.  **Кастомные репозитории:** Можно указать URL к собственному репозиторию компании.

**Конфигурация в `build.gradle.kts`:**
```kotlin
repositories {
    mavenCentral()  // Основной источник
    google()        // Для Android библиотек
    maven(url = "https://jitpack.io") // Кастомный репозиторий
}
```

**Процесс загрузки:**
1.  Gradle ищет зависимость в указанных репозиториях **в порядке их объявления**.
2.  Если находит — скачивает в локальный кэш (`~/.gradle/caches`).
3.  При последующих сборках использует локальную копию.

### **Тестирование**

### **1) Пирамида тестирования. Примеры тестов каждого вида**
**Ответ:**
**Пирамида тестирования** — модель, показывающая соотношение разных типов тестов в проекте.

**Слои пирамиды (снизу вверх):**

1.  **Unit-тесты (70-80%):**
    - **Что тестируют:** Отдельные функции, классы, методы.
    - **Пример:** Тестирование функции `calculateDiscount()`, класса `UserValidator`.
    - **Особенности:** Быстрые, изолированные, не требуют внешних зависимостей.

2.  **Интеграционные тесты (15-20%):**
    - **Что тестируют:** Взаимодействие нескольких компонентов.
    - **Пример:** Тестирование работы с базой данных, вызов внешнего API, взаимодействие сервисов.
    - **Особенности:** Медленнее unit-тестов, требуют настройки окружения.

3.  **UI/E2E тесты (5-10%):**
    - **Что тестируют:** Полный сценарий от начала до конца с точки зрения пользователя.
    - **Пример:** Автоматизированное тестирование веб-интерфейса через Selenium, мобильное приложение через Espresso.
    - **Особенности:** Очень медленные, хрупкие, требуют полного окружения.

**Пример для интернет-магазина:**
- **Unit:** Тестирование класса `Cart`, который вычисляет сумму товаров.
- **Интеграционные:** Тестирование `OrderService`, который сохраняет заказ в БД и отправляет уведомление.
- **E2E:** Полный сценарий "пользователь заходит на сайт, выбирает товар, оформляет заказ".

### **2) Как писать юнит тесты на JUnit? Какие аннотации есть?**
**Ответ:**
**JUnit 5** — стандартный фреймворк для unit-тестирования в Java/Kotlin.

**Базовая структура теста:**
```kotlin
import org.junit.jupiter.api.Test
import org.junit.jupiter.api.Assertions.*

class CalculatorTest {
    
    @Test
    fun `addition should return sum of two numbers`() {
        // Arrange
        val calculator = Calculator()
        
        // Act
        val result = calculator.add(2, 3)
        
        // Assert
        assertEquals(5, result)
    }
    
    @Test
    fun `division by zero should throw exception`() {
        val calculator = Calculator()
        
        val exception = assertThrows<ArithmeticException> {
            calculator.divide(10, 0)
        }
        
        assertEquals("Division by zero", exception.message)
    }
}
```

**Основные аннотации JUnit 5:**

| Аннотация | Описание |
| :--- | :--- |
| **`@Test`** | Помечает метод как тестовый. |
| **`@BeforeEach`** | Метод выполняется перед КАЖДЫМ тестом. Используется для инициализации. |
| **`@AfterEach`** | Метод выполняется после КАЖДОГО теста. Используется для очистки. |
| **`@BeforeAll`** | `static` метод, выполняется один раз перед всеми тестами класса. |
| **`@AfterAll`** | `static` метод, выполняется один раз после всех тестов класса. |
| **`@DisplayName`** | Задает человеко-читаемое имя для теста. |
| **`@Disabled`** | Отключает тест. |
| **`@Nested`** | Позволяет создавать вложенные классы для группировки тестов. |
| **`@ParameterizedTest`** | Параметризованный тест (много данных для одного теста). |

**Пример с жизненным циклом:**
```kotlin
class UserServiceTest {
    companion object {
        @BeforeAll
        @JvmStatic
        fun setupAll() {
            println("Выполняется один раз перед всеми тестами")
        }
    }
    
    @BeforeEach
    fun setup() {
        println("Выполняется перед каждым тестом")
    }
    
    @Test
    fun test1() {
        println("Тест 1")
    }
    
    @AfterEach
    fun tearDown() {
        println("Выполняется после каждого теста")
    }
}
```

### **3) Что такое мок, стаб, фикстура**
**Ответ:**

**Фикстура (Fixture)** — **предустановленные данные** для тестов. Это объекты, которые используются в нескольких тестах.
```kotlin
// Фикстура — тестовые пользователи
val testUser = User(id = 1, name = "Test User", email = "test@example.com")
val adminUser = User(id = 2, name = "Admin", email = "admin@example.com", role = Role.ADMIN)
```

**Стаб (Stub)** — объект, который **возвращает предопределенные ответы** на вызовы методов. Стабы не проверяют, как их вызывают.
```kotlin
// Стаб UserRepository, который всегда возвращает тестового пользователя
val userRepositoryStub = object : UserRepository {
    override fun findById(id: Int): User? = testUser
    override fun save(user: User) = Unit // Ничего не делает
}

val userService = UserService(userRepositoryStub)
val user = userService.getUser(1) // Всегда получим testUser
```

**Мок (Mock)** — объект, который **регистрирует вызовы своих методов** и позволяет проверить, как и с какими параметрами они вызывались.
```kotlin
// Создаем мок
val mockUserRepository = mockk<UserRepository>()

// Настраиваем поведение
every { mockUserRepository.findById(1) } returns testUser

// Выполняем тестируемое действие
userService.notifyUser(1)

// Проверяем, что метод save был вызван с правильными параметрами
verify { mockUserRepository.save(any()) }
```

**Разница:**
- **Фикстура** — данные.
- **Стаб** — возвращает готовые ответы.
- **Мок** — проверяет взаимодействие.

**Библиотеки для Kotlin:** `mockk` (рекомендуется), `Mockito` с `mockito-kotlin`.

### **4) Зачем измерять покрытие кода тестами?**
**Ответ:**
**Покрытие кода (Code Coverage)** — метрика, показывающая, какой процент кода выполняется при запуске тестов.

**Зачем нужно:**
1.  **Поиск непротестированного кода:** Показывает, какие части кода никогда не выполняются в тестах.
2.  **Качество тестов:** Высокое покрытие — индикатор (но не гарантия!) хорошего тестирования.
3.  **Рефакторинг:** При высоком покрытии можно быть увереннее, что изменения не сломают существующую функциональность.
4.  **Стандарты разработки:** Во многих компаниях есть требования к минимальному покрытию (например, 80%).

**Типы покрытия:**
- **Line coverage:** Какая доля строк кода была выполнена.
- **Branch coverage:** Какая доля ветвлений (if/else, when) было пройдено.
- **Path coverage:** Все возможные пути выполнения (самое строгое).

**Инструменты:** **JaCoCo** — самый популярный инструмент для измерения покрытия в JVM-проектах.

**Ограничения:**
- **100% покрытие ≠ хорошие тесты:** Можно написать тесты, которые выполняют весь код, но не проверяют корректность.
- **Не показывает качество asserts:** Код может выполняться, но не проверяться должным образом.
- **Может создавать ложное чувство безопасности.**

**Настройка JaCoCo в Gradle:**
```kotlin
plugins {
    jacoco
}

jacoco {
    toolVersion = "0.8.8"
}

tasks.test {
    finalizedBy(tasks.jacocoTestReport) // Генерировать отчет после тестов
}

tasks.jacocoTestReport {
    reports {
        xml.required.set(true)
        html.required.set(true)
    }
}
```

## **🎭 Лекция 10: Аннотации, рефлексия и дженерики**

### **1) Что такое аннотации**
**Ответ:**
**Аннотация** — это специальная метаданная, которая добавляется к элементам кода (классам, функциям, свойствам, параметрам) для предоставления дополнительной информации. Сами по себе аннотации не изменяют поведение кода, но могут использоваться компилятором, инструментами сборки или фреймворками во время компиляции или выполнения.

**Аналогия из жизни:** Это как стикер-наклейка на коробке: "Осторожно, хрупкое!" или "Верх". Сама наклейка не меняет содержимое коробки, но дает важную информацию тем, кто с ней работает.

**Примеры встроенных аннотаций Kotlin:**
```kotlin
@Deprecated("Используйте newMethod() вместо этого")
fun oldMethod() { /* ... */ }

@Suppress("UNUSED")
val unusedVariable = 5

@JvmStatic
fun staticMethod() { /* ... */ }

@Test
fun shouldCalculateCorrectly() { /* ... */ }
```

### **2) Какие виды аннотации есть**
**Ответ:**
Аннотации можно классифицировать по нескольким критериям:

**1. По источнику:**
- **Встроенные в язык/стандартную библиотеку:** `@Deprecated`, `@Suppress`, `@JvmName`, `@Throws`
- **Фреймворковые:** `@Entity`, `@Service`, `@RestController`, `@Test`
- **Пользовательские:** Созданные разработчиком.

**2. По времени жизни (`@Retention`):**
- **SOURCE** — видны только в исходном коде, не попадают в скомпилированный байткод.
- **BINARY** — попадают в байткод, но недоступны через рефлексию во время выполнения.
- **RUNTIME** — сохраняются в байткоде и доступны через рефлексию (самые распространенные).

**3. По цели применения (`@Target`):**
- Аннотации для классов, функций, свойств, параметров, типов и т.д.

**4. По воздействию:**
- **Информационные:** Только предоставляют информацию (`@Deprecated`)
- **Активные:** Влияют на поведение компилятора или рантайма (`@JvmStatic`, `@Test`)

### **3) Как создать свою аннотацию**
**Ответ:**
Для создания аннотации используется ключевое слово `annotation class`.

**Базовый синтаксис:**
```kotlin
annotation class MyAnnotation
```

**Аннотация с параметрами:**
```kotlin
annotation class Author(
    val name: String,
    val date: String = "2024-01-01"  // Параметры по умолчанию
)

annotation class Route(
    val path: String,
    val method: HttpMethod = HttpMethod.GET
)
```

**Допустимые типы параметров:**
- Примитивные типы (Int, Long, Double, Boolean и т.д.)
- String
- KClass (например, `String::class`)
- Enum
- Другие аннотации
- Массивы вышеперечисленных типов

**Пример сложной аннотации:**
```kotlin
enum class Priority { LOW, MEDIUM, HIGH }

annotation class Scheduled(
    val cron: String,
    val priority: Priority = Priority.MEDIUM,
    val enabled: Boolean = true
)

// Использование
@Scheduled(cron = "0 * * * * *", priority = Priority.HIGH)
fun cleanupJob() { /* ... */ }
```

### **4) Аннотации Target и Retention**
**Ответ:**
Это **мета-аннотации** — аннотации для аннотаций, которые определяют их поведение.

**1. `@Target`** — указывает, к каким элементам кода можно применять аннотацию.

**Доступные значения (из `AnnotationTarget`):**
- `CLASS` — классы, интерфейсы, объекты
- `FUNCTION` — функции (включая геттеры/сеттеры)
- `PROPERTY` — свойства
- `FIELD` — поля (включая backing-поля свойств)
- `VALUE_PARAMETER` — параметры функций
- `TYPE` — типы в объявлениях
- `TYPE_PARAMETER` — параметры типов (дженерики)
- И другие...

**Пример:**
```kotlin
@Target(AnnotationTarget.CLASS, AnnotationTarget.FUNCTION)
annotation class ExperimentalFeature

@ExperimentalFeature // OK - класс
class MyClass {
    @ExperimentalFeature // OK - функция
    fun myMethod() { /* ... */ }
    
    // @ExperimentalFeature // Ошибка - нельзя применить к свойству
    // val property = 5
}
```

**2. `@Retention`** — определяет, сохраняется ли аннотация в скомпилированном коде и доступна ли она через рефлексию.

**Доступные значения (из `AnnotationRetention`):**
- `SOURCE` — аннотация видна только в исходном коде, не сохраняется в байткоде.
- `BINARY` — аннотация сохраняется в байткоде, но недоступна через рефлексию.
- `RUNTIME` — аннотация сохраняется в байткоде и доступна через рефлексию (по умолчанию в Kotlin).

**Пример:**
```kotlin
@Retention(AnnotationRetention.SOURCE)
annotation class SuppressWarning  // Только для компилятора

@Retention(AnnotationRetention.RUNTIME)
annotation class ApiEndpoint(val path: String)  // Для фреймворков во время выполнения
```

**Полный пример создания аннотации:**
```kotlin
@Target(AnnotationTarget.CLASS, AnnotationTarget.FUNCTION)
@Retention(AnnotationRetention.RUNTIME)
annotation class RestController(
    val path: String = "/"
)

@RestController("/api/users")
class UserController {
    @RestController("/list")
    fun getUsers() { /* ... */ }
}
```

### **5) Что такое рефлексия и зачем она нужна. KClass**
**Ответ:**
**Рефлексия (Reflection)** — это механизм, позволяющий программе исследовать и модифицировать свою собственную структуру во время выполнения. В Kotlin рефлексия предоставляется через библиотеку `kotlin-reflect`.

**Зачем нужна рефлексия:**
1.  **Интроспекция:** Получение информации о классах, их свойствах, методах, конструкторах.
2.  **Динамическое создание и вызов:** Создание объектов, вызов методов по имени.
3.  **Работа с аннотациями:** Поиск элементов с определенными аннотациями.
4.  **Фреймворки и библиотеки:** Сериализация/десериализация, DI-контейнеры, ORM, валидация.
5.  **Генерация кода и плагины:** Анализ структуры кода для генерации дополнительного кода.

**`KClass<T>`** — основной интерфейс рефлексии в Kotlin, представляющий класс во время выполнения. Аналог `Class<T>` в Java, но с поддержкой Kotlin-специфичных фич (nullable типы, свойства и т.д.).

**Как получить `KClass`:**
```kotlin
// 1. Через ::class (статически)
val stringClass: KClass<String> = String::class

// 2. Из объекта
val obj = "Hello"
val objClass: KClass<out String> = obj::class

// 3. Для дженериков с reified (только в inline-функциях)
inline fun <reified T> getClass(): KClass<T> = T::class
```

**Что можно делать с `KClass`:**
```kotlin
data class Person(val name: String, val age: Int)

fun exploreClass(cls: KClass<*>) {
    println("Имя класса: ${cls.simpleName}")
    println("Полное имя: ${cls.qualifiedName}")
    
    println("\nКонструкторы:")
    cls.constructors.forEach { println("  $it") }
    
    println("\nСвойства:")
    cls.memberProperties.forEach { println("  ${it.name}: ${it.returnType}") }
    
    println("\nФункции:")
    cls.memberFunctions.forEach { println("  ${it.name}") }
    
    println("\nАннотации:")
    cls.annotations.forEach { println("  $it") }
}

// Использование
exploreClass(Person::class)
```

**Пример практического использования:**
```kotlin
// Сериализация с использованием рефлексии
fun serialize(obj: Any): Map<String, Any?> {
    return obj::class.memberProperties
        .associate { prop ->
            prop.name to prop.get(obj)
        }
}

val person = Person("Alice", 30)
val json = serialize(person) // {"name": "Alice", "age": 30}
```

### **6) Что такое дженерики. Отличие от Any**
**Ответ:**
**Дженерики (Generics, обобщения)** — механизм, позволяющий писать код, который работает с разными типами данных, сохраняя типобезопасность.

**Основная идея:** Создание классов, интерфейсов и функций, которые могут работать с любым типом, но тип указывается при использовании.

**Отличие от `Any`:**
- **`Any`** — это **конкретный тип** (супертип всех классов в Kotlin). При использовании `Any` теряется информация о конкретном типе.
- **Дженерики** — это **шаблон**, который сохраняет информацию о типе.

**Пример сравнения:**
```kotlin
// С использованием Any (ПЛОХО)
class BoxWithAny(val value: Any) {
    fun getValue(): Any = value
}

val anyBox = BoxWithAny("Hello")
val str = anyBox.getValue() as String  // Небезопасный каст! Может быть ClassCastException

// С использованием дженериков (ХОРОШО)
class Box<T>(val value: T) {
    fun getValue(): T = value  // Тип сохраняется!
}

val stringBox = Box("Hello")
val strSafe = stringBox.getValue()  // Тип String известен компилятору, каст не нужен

val intBox = Box(42)
val num = intBox.getValue()  // Тип Int
```

**Преимущества дженериков перед `Any`:**
1.  **Типобезопасность:** Ошибки обнаруживаются на этапе компиляции, а не выполнения.
2.  **Отсутствие кастов:** Не нужно приводить типы вручную.
3.  **Более чистый код:** Компилятор знает типы и может предоставлять автодополнение.
4.  **Повторное использование:** Один обобщенный код работает со многими типами.

### **7) Ограничения типов для дженериков**
**Ответ:**
**Ограничения типов (Type bounds)** позволяют указать, что параметр типа должен быть подтипом определенного класса или реализовывать определенный интерфейс.

**Верхнее ограничение (Upper bound) — `:`**
Указывает, что тип должен быть подтипом указанного класса/интерфейса.
```kotlin
// T должен быть подтипом Number
fun <T : Number> sum(list: List<T>): Double {
    return list.sumOf { it.toDouble() }
}

val ints = listOf(1, 2, 3)
val sumInts = sum(ints)  // OK: Int наследует Number

val strings = listOf("a", "b", "c")
// val sumStrings = sum(strings) // Ошибка: String не наследник Number
```

**Несколько ограничений — `where`:**
Когда тип должен удовлетворять нескольким условиям одновременно.
```kotlin
// T должен быть Comparable<T> И CharSequence
fun <T> maxLength(first: T, second: T): T 
    where T : Comparable<T>, T : CharSequence {
    return if (first.length > second.length) first else second
}

val result = maxLength("hello", "world")  // OK: String implements both
// val error = maxLength(1, 2)  // Ошибка: Int не CharSequence
```

**Ограничения в объявлении класса:**
```kotlin
// Все элементы списка должны быть Comparable
class SortedList<T : Comparable<T>> {
    private val items = mutableListOf<T>()
    
    fun add(item: T) {
        items.add(item)
        items.sort()
    }
}

val intList = SortedList<Int>()  // OK: Int implements Comparable<Int>
val stringList = SortedList<String>()  // OK: String implements Comparable<String>

class Person(val name: String)
// val personList = SortedList<Person>()  // Ошибка: Person не Comparable
```

**Нижнее ограничение (Lower bound)** в Kotlin явно не поддерживается, но достигается через контравариантность (`in`).

**Важность ограничений:**
1.  **Безопасность:** Гарантирует, что тип имеет нужные методы/свойства.
2.  **Выразительность:** Делает код более понятным.
3.  **Гибкость:** Позволяет писать более общий, но безопасный код.

### **8) In, Out (Вариантность)**
**Ответ:**
**Вариантность (Variance)** определяет, как отношения между обобщенными типами связаны с отношениями между их параметрами типов.

В Kotlin есть три вида вариантности:

**1. Инвариантность (Invariant) — по умолчанию**
Типы считаются связанными только если их параметры типов идентичны.
```kotlin
class Box<T>(var item: T)

val intBox: Box<Int> = Box(42)
// val anyBox: Box<Any> = intBox  // ОШИБКА! Box<Int> ≠ Box<Any>
// val numberBox: Box<Number> = intBox  // ОШИБКА!
```

**2. Ковариантность (Covariant) — `out`**
Позволяет использовать более конкретный тип вместо более общего. Обозначается `out T`.
- Тип `Producer<Dog>` может использоваться там, где ожидается `Producer<Animal>`.
- **Производитель (producer)** значений типа `T`: можно только читать (`get`), но нельзя записывать (`set`).

```kotlin
// Ковариантный интерфейс - только производит значения
interface Producer<out T> {
    fun produce(): T  // T только в исходящей позиции (возвращаемый тип)
    // fun consume(item: T)  // ОШИБКА! T во входящей позиции
}

class DogProducer : Producer<Dog> {
    override fun produce(): Dog = Dog()
}

fun handleAnimals(producer: Producer<Animal>) {
    val animal: Animal = producer.produce()
}

val dogProducer: Producer<Dog> = DogProducer()
handleAnimals(dogProducer)  // OK! Producer<Dog> может использоваться как Producer<Animal>
```

**3. Контравариантность (Contravariant) — `in`**
Позволяет использовать более общий тип вместо более конкретного. Обозначается `in T`.
- Тип `Consumer<Animal>` может использоваться там, где ожидается `Consumer<Dog>`.
- **Потребитель (consumer)** значений типа `T`: можно только записывать (`set`), но нельзя читать (`get`).

```kotlin
// Контравариантный интерфейс - только потребляет значения
interface Consumer<in T> {
    fun consume(item: T)  // T только во входящей позиции (параметр)
    // fun produce(): T  // ОШИБКА! T в исходящей позиции
}

class AnimalConsumer : Consumer<Animal> {
    override fun consume(item: Animal) {
        println("Потребляю $item")
    }
}

fun handleDogs(consumer: Consumer<Dog>) {
    consumer.consume(Dog())
}

val animalConsumer: Consumer<Animal> = AnimalConsumer()
handleDogs(animalConsumer)  // OK! Consumer<Animal> может использоваться как Consumer<Dog>
```

**Правила запоминания (мнемоника):**
- **`out`** — как **исходящий** поток (можно только читать).
- **`in`** — как **входящий** поток (можно только писать).
- **PECS** (Producer Extends, Consumer Super) из Java:
    - **Producer = `out`** = получаем от него значения.
    - **Consumer = `in`** = передаем ему значения.

**Пример из стандартной библиотеки:**
```kotlin
// List в Kotlin - ковариантный производитель
interface List<out E> : Collection<E> {
    operator fun get(index: Int): E  // Только чтение
    // fun add(element: E)  // Нет такого метода в интерфейсе List
}

// MutableList - инвариантный (и производитель, и потребитель)
interface MutableList<E> : List<E>, MutableCollection<E> {
    override fun add(element: E): Boolean  // И чтение, и запись
}

fun processStrings(list: List<String>) { /* ... */ }
val strings: List<String> = listOf("a", "b", "c")
val anys: List<Any> = strings  // OK! List ковариантна

fun addStrings(list: MutableList<String>) { /* ... */ }
val mutableStrings: MutableList<String> = mutableListOf("a", "b")
// val mutableAnys: MutableList<Any> = mutableStrings  // ОШИБКА! MutableList инвариантна
```

**Star-projections (`*`):**
Когда тип неизвестен, но нужно указать вариантность:
```kotlin
fun printFirst(list: List<*>) {  // Эквивалентно List<out Any?>
    if (list.isNotEmpty()) {
        println(list.first())  // Можем читать как Any?
    }
}

printFirst(listOf(1, 2, 3))    // OK
printFirst(listOf("a", "b"))   // OK
```

**Практическое применение:**
- **`out`** — для иммутабельных коллекций, фабрик.
- **`in`** — для компараторов, обработчиков событий.
- Без модификаторов — для мутабельных коллекций, где нужно и читать, и писать.

## **⚡ Лекция 11: Многопоточность**

### **1) Зачем выполнять что-то параллельно?**
**Ответ:**
Параллельное выполнение нужно для решения нескольких ключевых задач:

1. **Использование ресурсов процессора:** Современные процессоры имеют несколько ядер. Последовательная программа использует только одно ядро, оставляя остальные простаивающими. Параллелизм позволяет загрузить все ядра.

2. **Улучшение отзывчивости (responsiveness):** В GUI-приложениях (Android, десктоп) долгие операции (сеть, БД, вычисления) не должны блокировать основной поток, иначе интерфейс "зависнет".

3. **Повышение производительности (throughput):** Обработка большого объема данных быстрее при распределении по нескольким потокам/процессам.

4. **Обработка множества запросов одновременно:** Серверные приложения должны обслуживать тысячи клиентов одновременно.

5. **Работа с блокирующими операциями:** Ожидание ввода-вывода (I/O) — сети, диска — не должно блокировать всю программу.

**Пример:** Веб-браузер:
- Один поток рендерит страницу
- Другой загружает изображения
- Третий выполняет JavaScript
- Все это происходит параллельно

### **2) Потоки и процессы. В чем особенности?**
**Ответ:**

| Характеристика | Процесс (Process) | Поток (Thread) |
| :--- | :--- | :--- |
| **Определение** | Изолированный экземпляр выполняющейся программы. | "Легковесный" поток выполнения внутри процесса. |
| **Память** | Имеет собственную **изолированную** память (heap). | **Разделяет** память с другими потоками того же процесса. |
| **Создание** | Тяжелая операция, требует выделения памяти. | Легкая, использует память процесса. |
| **Изоляция** | Высокая. Сбой в одном процессе не влияет на другие. | Низкая. Сбой в потоке может "уронить" весь процесс. |
| **Коммуникация** | Межпроцессное взаимодействие (IPC) сложное: pipes, sockets, shared memory. | Простое взаимодействие через общую память. |
| **Пример** | Запуск браузера и текстового редактора — два процесса. | В браузере: один поток — интерфейс, другой — загрузка. |

**Аналогия:**
- **Процесс** — это фабрика со своими помещениями, складами, охраной.
- **Потоки** — это рабочие внутри одной фабрики, которые могут общаться напрямую и использовать общие ресурсы.

**В Java/Kotlin:** Мы работаем в основном с потоками (Thread API). Процессы создаются редко, для запуска внешних программ.

### **3) Что такое конкурентность и параллелизм? С примерами**
**Ответ:**
Это разные, но связанные концепции:

**Конкурентность (Concurrency)** — **способность выполнять несколько задач "одновременно"** за счет переключения между ними на одном ядре. Это про структуру программы.
```kotlin
// Конкурентность: задачи начинаются, выполняются и завершаются
// в перекрывающиеся периоды времени, но не обязательно в один момент
```

**Параллелизм (Parallelism)** — **фактическое одновременное выполнение нескольких задач на разных ядрах/процессорах**. Это про исполнение.
```kotlin
// Параллелизм: задачи выполняются физически одновременно
```

**Аналогия:**
- **Конкурентность** — один повар готовит суп и салат, переключаясь между ними.
- **Параллелизм** — два повара работают одновременно: один на суп, другой на салат.

**Пример в коде:**
```kotlin
// Конкурентность (корутины)
suspend fun concurrentExample() {
    coroutineScope {
        launch { task1() } // Начинаем задачу 1
        launch { task2() } // Начинаем задачу 2
        // Обе задачи выполняются конкурентно
    }
}

// Параллелизм (потоки)
fun parallelExample() {
    val thread1 = Thread { task1() }
    val thread2 = Thread { task2() }
    thread1.start() // Запускаем на ядре 1
    thread2.start() // Запускаем на ядре 2
    // Задачи выполняются параллельно, если есть свободные ядра
}
```

**Важно:** Параллелизм возможен только при наличии нескольких ядер/процессоров. Конкурентность возможна и на одном ядре.

### **4) Корутины. Что это такое? Как можно создать?**
**Ответ:**
**Корутины (Coroutines)** — это "легковесные потоки", механизм для асинхронного и конкурентного программирования в Kotlin. Они не являются потоками ОС, а работают поверх них.

**Основные характеристики:**
1. **Легковесные:** Тысячи корутин могут работать на одном потоке.
2. **Дешевое создание и переключение:** Нет накладных расходов на переключение контекста ОС.
3. **Структурированный параллелизм:** Иерархический родитель-потомок, автоматическая отмена.
4. **Отмена (cancellation):** Встроенная поддержка отмены корутин.
5. **Исключения:** Распространение исключений через иерархию.

**Как создать корутины:**

**1. Запуск корутины с `launch`:**
```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking { // Создает корутину-обертку
    println("Main starts: ${Thread.currentThread().name}")
    
    launch { // Запускает новую корутину
        delay(1000) // Неблокирующая задержка
        println("Coroutine 1: ${Thread.currentThread().name}")
    }
    
    launch {
        delay(500)
        println("Coroutine 2: ${Thread.currentThread().name}")
    }
    
    println("Main ends: ${Thread.currentThread().name}")
}
// Вывод может быть:
// Main starts: main
// Main ends: main
// Coroutine 2: main
// Coroutine 1: main
```

**2. Асинхронное выполнение с `async`/`await`:**
```kotlin
fun main() = runBlocking {
    val deferredResult: Deferred<Int> = async {
        delay(1000)
        42 // Возвращает результат
    }
    
    println("Выполняем другие задачи...")
    val result = deferredResult.await() // Ожидаем результат
    println("Результат: $result")
}
```

**3. Разные диспетчеры (dispatchers):**
```kotlin
fun main() = runBlocking {
    // Default - для CPU-интенсивных операций
    launch(Dispatchers.Default) {
        println("Default: ${Thread.currentThread().name}")
    }
    
    // IO - для операций ввода-вывода
    launch(Dispatchers.IO) {
        println("IO: ${Thread.currentThread().name}")
    }
    
    // Main - для UI (Android, JavaFX)
    // launch(Dispatchers.Main) { ... }
    
    // Unconfined - не привязан к конкретному потоку
    launch(Dispatchers.Unconfined) {
        println("Unconfined: ${Thread.currentThread().name}")
    }
    
    // Собственный пул потоков
    launch(newSingleThreadContext("MyThread")) {
        println("Custom: ${Thread.currentThread().name}")
    }
}
```

**4. Структурированный параллелизм:**
```kotlin
fun main() = runBlocking {
    // Родительская корутина
    val parentJob = launch {
        println("Parent started")
        
        // Дочерние корутины
        launch {
            delay(1000)
            println("Child 1 completed")
        }
        
        launch {
            delay(2000)
            println("Child 2 completed")
        }
    }
    
    delay(500)
    parentJob.cancel() // Отменяем родителя → отменяются все дети
    println("Parent cancelled")
}
```

### **5) Проблемы многопоточности**
**Ответ:**
При работе с несколькими потоками/корутинами возникают классические проблемы параллельного программирования:

**1. Состояние гонки (Race Condition):**
Когда результат зависит от порядка выполнения потоков.
```kotlin
var counter = 0

fun main() = runBlocking {
    val jobs = List(1000) {
        launch(Dispatchers.Default) {
            repeat(1000) {
                counter++ // НЕАТОМАРНАЯ операция!
            }
        }
    }
    jobs.forEach { it.join() }
    println("Counter = $counter") // Не 1_000_000!
}
// Проблема: counter++ это фактически:
// 1. Прочитать значение
// 2. Увеличить на 1
// 3. Записать значение
// Между этими шагами другие потоки могут изменить counter
```

**2. Взаимная блокировка (Deadlock):**
Два или более потока блокируют друг друга, ожидая ресурсы.
```kotlin
val resourceA = Any()
val resourceB = Any()

fun main() {
    Thread {
        synchronized(resourceA) {
            println("Thread 1: locked A")
            Thread.sleep(100)
            synchronized(resourceB) { // Ждет B
                println("Thread 1: locked B")
            }
        }
    }.start()
    
    Thread {
        synchronized(resourceB) {
            println("Thread 2: locked B")
            Thread.sleep(100)
            synchronized(resourceA) { // Ждет A
                println("Thread 2: locked A")
            }
        }
    }.start()
    // Оба потока заблокированы навсегда
}
```

**3. Голодание (Starvation):**
Поток не может получить доступ к ресурсам, потому что другие потоки монополизируют их.
```kotlin
val lock = Any()

fun main() {
    // Поток с высоким приоритетом постоянно занимает lock
    Thread {
        while (true) {
            synchronized(lock) {
                // Долгая операция
                Thread.sleep(1000)
            }
        }
    }.apply { priority = Thread.MAX_PRIORITY }.start()
    
    // Поток с низким приоритетом никогда не получит lock
    Thread {
        while (true) {
            synchronized(lock) { // Никогда не выполнится
                println("Low priority thread got lock!")
            }
        }
    }.apply { priority = Thread.MIN_PRIORITY }.start()
}
```

**4. Инверсия приоритетов (Priority Inversion):**
Поток с низким приоритетом удерживает ресурс, нужный потоку с высоким приоритетом.

**5. Проблема производителя-потребителя (Producer-Consumer):**
Синхронизация между потоками, которые производят и потребляют данные.

**Решения в Kotlin:**

**1. Атомарные операции и примитивы синхронизации:**
```kotlin
import java.util.concurrent.atomic.AtomicInteger

val atomicCounter = AtomicInteger(0)

fun main() = runBlocking {
    val jobs = List(1000) {
        launch(Dispatchers.Default) {
            repeat(1000) {
                atomicCounter.incrementAndGet() // АТОМАРНАЯ операция
            }
        }
    }
    jobs.forEach { it.join() }
    println("Counter = ${atomicCounter.get()}") // 1_000_000
}
```

**2. Мьютексы (Mutex):**
```kotlin
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock

val mutex = Mutex()
var counter = 0

suspend fun increment() {
    mutex.withLock { // Взаимоисключающая блокировка
        counter++
    }
}
```

**3. Семафоры (Semaphore):**
```kotlin
import kotlinx.coroutines.sync.Semaphore

val semaphore = Semaphore(1) // Только один поток одновременно

suspend fun accessResource() {
    semaphore.acquire()
    try {
        // Критическая секция
    } finally {
        semaphore.release()
    }
}
```

**4. Потокобезопасные коллекции:**
```kotlin
import java.util.concurrent.ConcurrentHashMap

val concurrentMap = ConcurrentHashMap<String, Int>()
val threadSafeList = Collections.synchronizedList(mutableListOf<Int>())
```

**5. Корректное использование корутин (асинхронные каналы, потоки):**
```kotlin
import kotlinx.coroutines.channels.Channel

val channel = Channel<Int>() // Потокобезопасный канал

suspend fun producer() {
    for (i in 1..10) {
        channel.send(i) // Безопасная отправка
    }
    channel.close()
}

suspend fun consumer() {
    for (value in channel) { // Безопасное получение
        println("Received: $value")
    }
}
```

**6. Акторы (Actors):**
```kotlin
import kotlinx.coroutines.channels.actor

sealed class CounterMsg
object IncMsg : CounterMsg()
class GetMsg(val response: CompletableDeferred<Int>) : CounterMsg()

fun counterActor() = GlobalScope.actor<CounterMsg> {
    var counter = 0
    for (msg in channel) {
        when (msg) {
            is IncMsg -> counter++
            is GetMsg -> msg.response.complete(counter)
        }
    }
}

suspend fun main() {
    val counter = counterActor()
    
    // Множество корутин отправляют сообщения
    val jobs = List(1000) {
        GlobalScope.launch {
            repeat(1000) {
                counter.send(IncMsg)
            }
        }
    }
    
    jobs.forEach { it.join() }
    
    val response = CompletableDeferred<Int>()
    counter.send(GetMsg(response))
    println("Counter = ${response.await()}")
    counter.close()
}
```

**Ключевые принципы безопасного многопоточного программирования:**
1. **Неизменяемость (Immutability):** Используйте `val` и иммутабельные структуры данных.
2. **Изоляция потоков:** Каждый поток работает со своими данными.
3. **Синхронизация:** Используйте примитивы для доступа к общим ресурсам.
4. **Атомарность:** Используйте атомарные операции.
5. **Проектирование без блокировок (Lock-free):** По возможности избегайте блокировок.
